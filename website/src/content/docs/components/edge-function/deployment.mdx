The Edge Function is the only FORA component that providers deploy. This page covers the deployment model, configuration, secrets management, and onboarding procedure.

## Provider Onboarding Flow

```mermaid
sequenceDiagram
    participant Provider as Provider
    participant MO as Exchange Operator
    participant Origin as Provider's Origin
    participant CDN as Provider's CDN

    Provider->>MO: Sign resource access agreement
    MO-->>Provider: Exchange endpoint + fora.json

    Provider->>Origin: Publish /.well-known/fora.json
    Note over Origin: The provider's own file<br/>rsl.txt, if any, lives here too

    Provider->>CDN: Deploy edge function (platform-specific)
    Note over CDN: CloudFront: Lambda@Edge viewer-request function<br/>Cloudflare: wrangler deploy<br/>Fastly: fastly compute deploy

    Provider->>CDN: Verify: GET /.well-known/fora.json
    CDN->>Origin: Forward the request
    Origin-->>CDN: 200 OK + WellKnownManifest
    CDN-->>Provider: The origin's answer, unchanged

    Provider->>CDN: Verify: curl -A "GPTBot" /premium/article.html
    CDN-->>Provider: 403 + X-Content-Rules (+ X-FORA-Exchange)
```

Where the Exchange operator runs a publisher console, the console generates the file and the edge package for the provider: see [Publisher Onboarding](/getting-started/publisher-onboarding/).

## Simplest Possible Onboarding

The absolute minimum a provider needs to do:

1. **Get an Exchange endpoint** from their Exchange operator (one-time business relationship).
2. **Publish `fora.json`** on their own origin, at `/.well-known/fora.json`.
3. **Deploy the edge function** from the package the Exchange operator's console builds, or with a Terraform module (see [Distribution Formats](#distribution-formats)).
4. **Verify** -- `curl -I https://techcrunch.com/.well-known/fora.json` returns the origin's file through the edge function.

Target: **under 10 minutes** from Exchange operator contract to live edge function.

## Distribution Formats

The edge function is the edge worker in the reference implementation, [`src/edge`](https://github.com/FORA-Protocol/reference-implementation/tree/v1.1.0/src/edge). The same application runs on Cloudflare Workers, AWS Lambda@Edge and Fastly Compute. It reaches a provider's CDN in one of two formats.

### Format 1: Console Package

The Exchange operator's publisher console builds a package for the provider's domain, with the provider's settings in it: a Worker for Cloudflare, or a Lambda@Edge function for CloudFront. [Publisher Onboarding](/getting-started/publisher-onboarding/#install-the-package-on-your-cdn) gives the steps to install it.

### Format 2: Terraform Modules

The reference implementation's Terraform modules deploy the edge worker to the provider's own CDN account. They are in [`deploy/terraform/modules/`](https://github.com/FORA-Protocol/reference-implementation/tree/v1.1.0/deploy/terraform/modules) at release `v1.1.0`, and the examples below pin their `source` to that tag.

Each module deploys a bundle that you build first, from a checkout of the reference implementation. The build needs Node.js, npm and git. Neither module builds the bundle, and each fails the plan if the bundle is missing.

#### CloudFront

The [`aws-cloudfront-edge`](https://github.com/FORA-Protocol/reference-implementation/blob/v1.1.0/deploy/terraform/modules/aws-cloudfront-edge/README.md) module creates a CloudFront distribution in front of your origin, with the edge worker as its Lambda@Edge viewer-request function and an ACM certificate for your hostname. It creates no DNS record for the hostname. The [`route53-dns`](https://github.com/FORA-Protocol/reference-implementation/tree/v1.1.0/deploy/terraform/modules/route53-dns) module points the hostname at the distribution.

Lambda@Edge has no environment variables, so the edge worker's settings go inside the bundle. Write them to a JSON file, then build the bundle for the hostname the function serves. The build also needs `zip`.

```bash
git clone --branch v1.1.0 https://github.com/FORA-Protocol/reference-implementation.git
cd reference-implementation
cat > lambda-edge-config.json <<'EOF'
{
  "EXCHANGE_URL": "https://exchange.example.net",
  "EXCHANGE_WBA_URL": "https://exchange.example.net/.well-known/http-message-signatures-directory",
  "LICENSED_PATHS_JSON": "[\"/premium/\", \"/archive/\"]"
}
EOF
deploy/terraform/scripts/build-lambda-edge.sh lambda-edge-config.json news.example.com
```

The script writes `src/edge/dist/lambda-edge.zip` in the checkout. Every value in the settings file is a string. [`CONFIGURATION.md`](https://github.com/FORA-Protocol/reference-implementation/blob/v1.1.0/src/edge/CONFIGURATION.md) lists the settings. After a change to the settings, build the bundle again and apply again: the function runs what is in the zip.

Then write the Terraform configuration in the directory that holds the checkout:

```hcl
provider "aws" {
  region = "us-east-1" # Lambda@Edge and the CloudFront certificate live here
}

data "aws_route53_zone" "site" {
  name = "example.com"
}

module "fora_edge" {
  source = "github.com/FORA-Protocol/reference-implementation//deploy/terraform/modules/aws-cloudfront-edge?ref=v1.1.0"

  lambda_zip_path = "${path.root}/reference-implementation/src/edge/dist/lambda-edge.zip"
  hostname        = "news.example.com"
  zone_id         = data.aws_route53_zone.site.zone_id
  origin_domain   = "origin.example.com"
}

module "fora_dns" {
  source = "github.com/FORA-Protocol/reference-implementation//deploy/terraform/modules/route53-dns?ref=v1.1.0"

  zone_id   = data.aws_route53_zone.site.zone_id
  a_records = {}
  alias_records = {
    news = {
      target_domain  = module.fora_edge.distribution_domain_name
      target_zone_id = module.fora_edge.distribution_hosted_zone_id
    }
  }
}
```

The module needs an AWS provider in `us-east-1`, because Lambda@Edge functions and the certificate CloudFront serves are created there. With any other region, the plan fails. If your configuration's default AWS provider is in another region, declare a second provider with `alias = "us_east_1"` and `region = "us-east-1"`, and pass it to the module with `providers = { aws = aws.us_east_1 }`.

`origin_domain` is the host CloudFront fetches content from, and it must serve TLS for its own name. The module README describes the two optional inputs, `name_prefix` and `price_class`, and the outputs.

The module always creates a new distribution. To run the edge worker on a distribution you already have, create the function from the same zip and attach it, as the [AWS CloudFront steps](/getting-started/publisher-onboarding/#aws-cloudfront) in Publisher Onboarding describe.

#### Cloudflare

The [`cloudflare-edge`](https://github.com/FORA-Protocol/reference-implementation/blob/v1.1.0/deploy/terraform/modules/cloudflare-edge/README.md) module uploads the edge worker as a Worker and creates its routes. The Worker's settings are module inputs, so the bundle needs none. Build it:

```bash
git clone --branch v1.1.0 https://github.com/FORA-Protocol/reference-implementation.git
reference-implementation/deploy/terraform/scripts/build-cloudflare-edge.sh
```

The script writes `src/edge/dist/worker.mjs` in the checkout. Then write the Terraform configuration in the directory that holds the checkout:

```hcl
terraform {
  required_providers {
    cloudflare = {
      source  = "cloudflare/cloudflare"
      version = "~> 4.52"
    }
  }
}

provider "cloudflare" {} # reads the API token from CLOUDFLARE_API_TOKEN

data "cloudflare_zone" "site" {
  name = "example.com"
}

module "fora_edge" {
  source = "github.com/FORA-Protocol/reference-implementation//deploy/terraform/modules/cloudflare-edge?ref=v1.1.0"

  account_id         = data.cloudflare_zone.site.account_id
  zone_id            = data.cloudflare_zone.site.id
  worker_bundle_path = "${path.root}/reference-implementation/src/edge/dist/worker.mjs"
  route_patterns     = ["news.example.com/*"]

  exchange_url        = "https://exchange.example.net"
  exchange_wba_url    = "https://exchange.example.net/.well-known/http-message-signatures-directory"
  same_zone_origin    = "true"
  licensed_paths_json = jsonencode(["/premium/", "/archive/"])
}
```

The module requires an origin mode. `same_zone_origin = "true"` sends the requests the Worker lets through on to the origin the zone already routes the hostname to. To send them to another host, set `origin_url` to its URL instead. If the hostname has no DNS record on the zone yet, set `worker_hostname` to it, and the module creates a proxied placeholder record.

Cloudflare's zone protections, such as WAF managed rules and Bot Fight Mode, run before the Worker. The module README describes how to exempt the Worker's hostnames, and lists every input. The reference implementation also has a ready-made root configuration for this module, [`deploy/terraform/stacks/edge`](https://github.com/FORA-Protocol/reference-implementation/tree/v1.1.0/deploy/terraform/stacks/edge), with a [step-by-step guide](https://github.com/FORA-Protocol/reference-implementation/blob/v1.1.0/deploy/terraform/docs/deploy-edge-standalone.md).

## Environment Configuration

### What the Edge Function Needs to Know

| Configuration Item | Source | Change Frequency | Example |
|---|---|---|---|
| Exchange domain | Provider-Exchange contract | Rarely | `exchange.ssp.com` |
| Origin | Deployment config | Rarely | `https://origin.techcrunch.com`, or the CDN's own configured origin |
| Protected path patterns | Provider editorial policy | Monthly | `["/premium/*", "/archive/*"]` |
| Bot User-Agent patterns | FORA community list | Weekly | `["ClaudeBot", "GPTBot", ...]` |
| Exchange key directory | Provider-Exchange contract | Rarely | `https://exchange.example/.well-known/http-message-signatures-directory` |
| Pinned verify keys | Optional; skips the directory fetch | Rarely | `[{"kty":"OKP","crv":"Ed25519",...}]` |
| Max URL TTL | Policy | Rarely | `300` (seconds) |
| Single-use enabled | Policy | Rarely | `true` |
| Agent binding enabled | Policy | Rarely | `false` |

### Discovery Headers on the 403

The edge function's refusal of an unlicensed bot carries the two FORA edge discovery headers. Neither header carries the Exchange endpoint URL.

| Header | Value | Built from |
|---|---|---|
| `X-Content-Rules` | `https://techcrunch.com/.well-known/fora.json` | The host of the refused request. It is the URL of the provider's own manifest, which the provider serves from its origin, never an Exchange URL. |
| `X-FORA-Exchange` | `exchange.ssp.com` | The Exchange domain, as a bare domain in the form of `Offer.exchange`. Send it only for an Exchange the provider's manifest lists, and only together with `X-Content-Rules`. |

An agent that receives `X-FORA-Exchange` resolves the Exchange's endpoint from the Exchange's own `/.well-known/fora.json`, and treats the provider's manifest as the authority on which Exchanges sell the content. See [Edge discovery headers](/protocol/discovery-paths/#edge-discovery-headers) for the rules.

### Configuration Sources

```mermaid
graph TD
    subgraph "Config Sources"
        ENV[Environment Variables<br/>Exchange directory URL,<br/>Exchange domain, mode flags]
        KV[Edge KV Store<br/>Bot patterns,<br/>content policy]
        INLINE[Inline / Compiled<br/>Protocol version]
        CMS[CMS API<br/>Content policies,<br/>path rules]
    end

    subgraph "Edge Function"
        CONFIG_LOADER[Config Loader<br/>Merges all sources<br/>Validates on load]
        HANDLER[Request Handler]
    end

    ENV --> CONFIG_LOADER
    KV --> CONFIG_LOADER
    INLINE --> CONFIG_LOADER
    CMS --> CONFIG_LOADER
    CONFIG_LOADER --> HANDLER
```

**Merge order** (later overrides earlier):

1. **Inline / compiled defaults** -- protocol version.
2. **Environment variables** -- the Exchange key directory URL, the Exchange domain, mode flags. No secret: the edge holds public keys only.
3. **Edge KV** -- bot patterns (updated frequently), content policy rules.
4. **CMS API** -- dynamic content policy (which paths are newly protected/released). Only fetched if CMS integration is configured. Cached at edge with TTL.

### Configuration Schema

```typescript
/**
 * Complete edge function configuration.
 * Serializable to JSON for storage in KV.
 * Secrets are resolved from environment, not stored here.
 */
interface EdgeConfigDocument {
  /** Config schema version (for forward compatibility). */
  config_version: "1.0";

  /** The X-FORA-Exchange value on a 403: the bare domain of an Exchange the
   * provider's fora.json lists (e.g. "exchange.example"), never a URL. */
  exchange_domain?: string;

  /** Content access policy. */
  content_policy: {
    /** Default policy for paths not matching any rule. */
    default: "open" | "licensed" | "blocked";
    /** Path-specific rules. Evaluated in order, first match wins. */
    rules: Array<{
      /** Glob pattern (e.g. "/premium/*"). */
      pattern: string;
      /** Policy for matching paths. */
      policy: "open" | "licensed" | "blocked";
    }>;
  };

  /** Bot detection configuration. */
  bot_detection: {
    /** User-Agent substrings to match (case-insensitive): training crawlers
     * and live fetchers, which get the 403 on licensed paths. */
    user_agent_patterns: string[];
    /** User-Agent substrings of AI search crawlers (case-insensitive). */
    ai_search_patterns?: string[];
    /** What an AI search crawler gets on a licensed path: "allow" passes it
     * through, "block" returns the 403. Defaults to "allow". */
    ai_search_policy?: "allow" | "block";
    /** Whether to use CDN-native bot scoring (platform-specific). */
    use_cdn_bot_score: boolean;
    /** CDN bot score threshold (0-100, lower = more likely bot). */
    cdn_bot_score_threshold?: number;
  };

  /** Signed URL verification configuration. */
  signing: {
    /** Exchange key directory the edge resolves `kid` against. */
    exchange_wba_url: string;
    /** Optional pinned public keys; a covering `kid` skips the fetch. */
    verify_keys?: JsonWebKey[];
    /** Whether to enforce agent identity binding. Defaults to true. */
    enforce_binding: boolean;
    /** Whether to enforce single-use URLs (best-effort, see Section 5.3). */
    single_use_enabled: boolean;
  };
}
```

## Secrets Management

- **The edge function holds no secret.** It verifies with a public key, so its signing configuration is a directory URL and, optionally, pinned public keys. Neither is confidential, and both may live in plain configuration or KV.
- Configuration is loaded once at function initialization (cold start), not per-request. Where a deployment does carry a secret for unrelated reasons, it belongs in the platform secret store, never in KV.

### Platform-Specific Wrangler Deployment (Cloudflare)

For Cloudflare Workers, use `wrangler` for deployment:

```bash
# Local development
cd packages/edge-function && npx wrangler dev

# Production deploy
cd packages/edge-function && npx wrangler deploy

# Point the worker at the Exchange key directory
npx wrangler deploy --var EXCHANGE_WBA_URL=https://exchange.example/.well-known/http-message-signatures-directory
```

### CDN-Specific Deployment Commands

| CDN | Deploy Command |
|---|---|
| Cloudflare | `npx wrangler deploy` |
| CloudFront | `terraform apply` with the `aws-cloudfront-edge` module |
| Fastly | `fastly compute deploy` |

## The Provider's Own Documents

`/.well-known/fora.json` and `/rsl.txt` are files on the provider's origin. The edge function forwards both addresses there for every client, ahead of all its checks, and has no setting for either: see [fora.json and rsl.txt Pass-Through](/components/edge-function/overview/#forajson-and-rsltxt-pass-through). The origin's `Cache-Control` reaches the agent unchanged, so the provider decides how long a document may be cached, and a change to either file takes effect without redeploying anything.

## Preventing Edge Function Bypass

The edge function is only effective if all requests to protected content pass through it. Bypass vectors and mitigations:

| Bypass Vector | Mitigation |
|---|---|
| Direct origin access (skipping CDN) | Origin should only accept requests from CDN IPs. Use origin shield, security groups, or origin access identity (CloudFront OAI/OAC). |
| Alternate domain pointing to same origin | All domains serving protected content must have the edge function deployed. |
| CDN cache serving stale content without re-verification | Set `Cache-Control: private` or short TTL on protected content. Or use CDN-native signed URL verification which applies to cached responses too. |
| Agent using a different path to the same content (URL alias) | Content policy rules must cover all URL patterns that resolve to protected content. |

## Verification Procedure

After deployment, verify with these checks:

1. `GET /.well-known/fora.json` with bot User-Agent returns the origin's file with `200 OK`. A `404` means the site has no file at that address. A `403` means something on the site refuses AI agents there, and they have to be let through.
2. `GET /rsl.txt` with bot User-Agent returns the origin's answer: valid RSL content with `200 OK`, or the origin's `404` if the provider has no RSL file.
3. `GET /premium/article.html` with bot User-Agent returns `403` with `X-Content-Rules` set to the provider's own `https://<domain>/.well-known/fora.json`, and, when configured, `X-FORA-Exchange` set to the bare domain of an Exchange that manifest lists (for example `exchange.ssp-example.com`, not a URL).
4. `GET /premium/article.html` with valid signed URL returns `200`.
5. `GET /premium/article.html` with expired signed URL returns `403`.
6. `GET /premium/article.html` with tampered signed URL returns `403`.
7. `GET /free/article.html` with bot User-Agent returns `200` (open content).
