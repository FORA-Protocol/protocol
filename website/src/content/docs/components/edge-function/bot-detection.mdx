The Edge Function detects AI crawlers accessing protected content without a signed URL and returns a `403 Forbidden` response directing them to the Exchange. Bot detection only applies to requests *without* signed URL parameters -- a valid signed URL always takes precedence.

## Detection Signals

Three layers of bot detection, from cheapest to most expensive:

### Layer 1: User-Agent String Matching (< 0.01ms)

Known AI crawler User-Agents. This is the primary detection mechanism.

```
# Well-known AI bot User-Agents (maintained list)
ClaudeBot/1.0           - Anthropic training crawler
anthropic-ai            - Anthropic inference/RAG
GPTBot/1.0              - OpenAI training crawler
ChatGPT-User            - OpenAI inference/RAG
CCBot/2.0               - Common Crawl
Google-Extended          - Google AI training
Googlebot-Extended       - Google AI training (alternate)
Bytespider              - ByteDance training crawler
PerplexityBot           - Perplexity AI
YouBot                  - You.com
Applebot-Extended        - Apple AI training
cohere-ai               - Cohere
Meta-ExternalAgent       - Meta AI training
Amazonbot               - Amazon AI
AI2Bot                  - Allen Institute for AI
Diffbot                 - Diffbot
Omgilibot               - Webz.io
FacebookBot             - Meta
fora-ai-buyer          - FORA protocol agent (self-identified)
```

The edge function maintains this list in configuration (KV store or inline config). The list is additive -- new bots are added, existing entries are never removed.

### Layer 2: CDN-Native Bot Classification (0ms -- pre-computed)

All major CDNs maintain their own bot classification databases:

- **Cloudflare**: `cf.bot_management.score` (0-99, lower = more likely bot), `cf.bot_management.verified_bot`, `cf.bot_management.ja3_hash`.
- **Akamai**: Bot Manager Premier -- behavioral analysis, device fingerprinting.
- **Fastly**: Signal Sciences WAF -- bot detection signals.
- **CloudFront**: AWS WAF Bot Control -- managed rule group with bot categorization.

These are available as request metadata without any computation cost at the edge. The edge function can check CDN-native bot signals as a second layer.

### Layer 3: Behavioral Signals (0ms -- pattern matching)

Heuristic patterns that indicate automated access:

- **Request rate**: More than N requests to protected paths within T seconds from the same IP.
- **Missing headers**: Real browsers send `Accept`, `Accept-Language`, `Accept-Encoding`. Bots often omit them.
- **No cookie/session**: Legitimate users have session cookies. First-time visitors get a redirect to set a cookie (but this interferes with bot protocol flow -- use sparingly).
- **Sequential path access**: Bots tend to walk paths sequentially (`/premium/1`, `/premium/2`, ...). Humans jump around.
- **TLS fingerprint**: JA3/JA4 fingerprint mismatches (User-Agent claims to be Chrome but TLS fingerprint is Python `requests`).

Layer 3 signals are supplementary. They can reduce false positives (bot with unknown User-Agent) but should not override a valid signed URL.

## Bot Classification Tiers

The edge function catches **cooperative AI bots** -- those that identify themselves via well-known User-Agent strings. It is not a replacement for the provider's CDN WAF. Both are required:

| Layer | What It Catches | Mechanism |
|---|---|---|
| **Edge function** (FORA) | Cooperative AI bots (ClaudeBot, GPTBot, etc.) | User-Agent string matching |
| **CDN WAF** | Everything else: disguised bots, credential stuffing, DDoS, scraping with spoofed UAs | Fingerprinting, behavioral analysis, rate limiting, ML models |

The edge function is **additive** to the WAF, not a replacement. It must deploy alongside existing WAF rules without conflict.

**Integration requirement**: on most CDNs the WAF and the bot product run *before* the edge function, so what they let through decides what the edge function sees. [Keeping CDN Bot Protection On](#keeping-cdn-bot-protection-on) says which requests they must let through, and how a provider can keep its bot product on in front of the edge function.

## Keeping CDN Bot Protection On

A request that the CDN's WAF or bot product blocks or challenges never reaches the edge function. Whatever the WAF and the bot product think of the client, two kinds of request MUST get through them:

- **Signed requests** on the hosts and paths where the edge function checks them: requests that carry the signed URL parameters `agent_id`, `exp`, `kid` and `sig` (see [Signed URL Verification](/components/edge-function/signed-url-verification/)).
- **GET and HEAD of the two provider documents**, `/.well-known/fora.json` and `/rsl.txt`, which have to reach the origin for every client. The edge function forwards them where it runs on them. Where it does not, as on a CloudFront cache behavior it is not associated with, the CDN fetches them from the origin itself.

Letting signed requests skip the bot product does not weaken access control where the edge function checks them. There, a request whose signature does not check out gets a `403` whether the client is a bot or a browser, so a forged signature is refused by the edge function instead of by the bot product. Two limits keep this true:

- **Limit the exception to where the edge function checks signed requests**: its hostnames, and the paths on which it checks signed URL parameters. The console's package checks them on every path it runs on: the whole hostname on Cloudflare, the paths of its cache behaviors on CloudFront. An edge function that checks them only on its protected paths needs the exception limited to those paths. A request that carries `sig` anywhere else reaches the origin with no signature check at all.
- **Match the parameter name exactly and case-sensitively**, the way the edge function reads it. A case-insensitive match lets `?SIG=x` past the bot product, while the edge function treats that request as unsigned, so a scraper that claims to be a browser is served the page.

A provider chooses one of two setups.

### Setup 1: the edge function decides for every client

This is the recommended setup. The bot product leaves the protected paths and the two documents to the edge function, and keeps protecting the rest of the site. Every cooperative AI bot without a license gets the edge function's `403` with `X-Content-Rules` and `X-FORA-Exchange` (see [The 403 Response](#the-403-response)), so it learns where to buy access.

### Setup 2: the bot product stays on, signed requests skip it

The bot product keeps blocking automated traffic on the protected paths too, with an exception for signed requests and the two documents. This setup has two costs:

- An AI bot without a license gets the CDN's own answer, an HTML block or challenge page or a short JSON message, without the discovery headers, so it does not learn where to buy access. Agents that already know the provider's `fora.json`, or find the content in an Exchange's catalog, are not affected.
- The exception matches the shape of a request, and that shape is public. Anyone can add `sig` to an address to pass the bot product. The edge function refuses each such request whose signature does not check out, so no content is released, but the bot product no longer filters that traffic.

The bot product also sees two automated readers of the provider's own setup. An Exchange that reads the provider's sitemap to build its catalog needs the sitemap exempted too, or the catalog stays empty. An onboarding console that checks the edge function by asking as an AI bot without a license gets the CDN's answer under this setup, so it cannot see the edge function: finish onboarding under setup 1, then add the exception.

To check the exception, ask for a protected page with a signature that cannot be valid:

```bash
curl -s -i -A "GPTBot/1.0" \
  "https://publisher.example/premium/article.html?sig=check"
# Expect: 403, content-type: application/json, a reason in the body.
#         Any other answer, such as an HTML page, means the CDN answered, and the
#         exception does not match.
```

Tell the edge function's answers from the CDN's by `content-type`, the body and the discovery headers. Headers such as `server: cloudflare` and `cf-ray` appear on the edge function's answers too.

### Cloudflare

WAF custom rules, managed rules and the bot products run before a Worker. Super Bot Fight Mode, on the Pro and Business plans, can be skipped by a WAF custom rule with the action **Skip** and only **All Super Bot Fight Mode rules** ticked, placed above every rule that blocks or challenges. For a provider at `publisher.example`:

```
http.host eq "publisher.example" and (any(http.request.uri.args.names[*] eq "sig") or http.request.uri.path in {"/.well-known/fora.json" "/rsl.txt"})
```

The expression names the host and no path, so it is safe only where the edge function runs on the whole hostname and checks every request that carries `sig` there, as the console's package does with the route `publisher.example/*`. The skip also takes these requests past Cloudflare's AI crawler and agent access policies, so they need no rule of their own.

The Free plan's Bot Fight Mode cannot be skipped by any rule, so setup 2 is not available there. AI Crawl Control blocks crawlers with a custom rule of its own, which the skip does not cover. Put that rule's expression in parentheses and add the skip expression after it, with `and not` in front, so the crawler block lets the same requests through on this host:

```
and not (http.host eq "publisher.example" and (any(http.request.uri.args.names[*] eq "sig") or http.request.uri.path in {"/.well-known/fora.json" "/rsl.txt"}))
```

AI Crawl Control answers a crawler it blocks with a `403` and the JSON `{"message":"Please contact the site owner for access."}`, not with an HTML page.

### CloudFront

AWS WAF evaluates a request before the Lambda@Edge viewer-request function. With the Bot Control managed rule group (`AWSManagedRulesBotControlRuleSet`), a scope-down statement, set inside the rule's `ManagedRuleGroupStatement`, leaves the exceptions out of what Bot Control inspects. The statement below matches `sig` on the query string with no text transformation, because a `SingleQueryArgument` match compares the name without regard to case. Its path statements remove dot segments and repeated slashes first (`NORMALIZE_PATH`), as CloudFront also does before it picks a cache behavior, so `/premium/../account/login?sig=x` is not taken for a protected path. It leaves a signed request out only on the provider's host and on the path prefix of the cache behavior the function is associated with:


## The 403 Response

When a bot is detected on a protected path without a signed URL:

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json
X-Content-Rules: https://techcrunch.com/.well-known/fora.json
X-FORA-Exchange: exchange.ssp-example.com
Cache-Control: no-store
```

```json
{
  "error": "Licensed content. Negotiate access via the Exchange.",
  "protocol": "FORA",
  "version": "1.0",
  "fora_json_url": "https://techcrunch.com/.well-known/fora.json"
}
```

**Header semantics** (the FORA edge discovery headers; the normative rules are in [Discovery Paths](/protocol/discovery-paths/#edge-discovery-headers)):
- `X-Content-Rules` -- the absolute URL of the provider's own manifest, `https://<provider domain>/.well-known/fora.json`. This is the key discovery mechanism for bots that did not check `fora.json`: the manifest carries the licensing terms and, in `exchanges[]`, the Exchanges that sell this content. It never points at an Exchange.
- `X-FORA-Exchange` -- optional. The bare domain of one Exchange that sells this content directly, in the same form as `Offer.exchange` (no scheme, no path). An agent can start discovery there without fetching the manifest first, resolving the Exchange's endpoint from the Exchange's own `fora.json`. It is an optimisation, not authorization: the edge sends it only beside `X-Content-Rules` and only for an Exchange the manifest lists, and when the two disagree the manifest wins.
- `Cache-Control: no-store` -- the 403 should not be cached. Content availability may change.

**Body semantics**:
- `error` -- human/machine readable explanation.
- `protocol` -- identifies this as a FORA protocol response, not a generic 403.
- `version` -- protocol version for forward compatibility.
- `fora_json_url` -- same as the `X-Content-Rules` header, in the body for agents that parse JSON responses. The body is informative; the headers are the protocol.

## Classification Algorithm

The detection algorithm follows a strict priority order to minimize false positives:

1. **Only process protected paths** -- never block requests to open content.
2. **Check for signed URL parameters first** -- if present, skip bot detection entirely and proceed to signature verification.
3. **User-Agent matching is exact substring match**, not fuzzy. Unknown User-Agents pass through.
4. **Never block based on behavioral signals alone** -- they supplement User-Agent detection, not replace it.

## False Positive Handling

A false positive (regular user blocked as bot) is worse than a false negative (bot not detected). The edge function should err on the side of allowing access:

- **Only block on protected paths** -- never block requests to open content.
- **Never block requests with valid signed URLs** -- signature verification overrides bot detection.
- **User-Agent matching is exact substring match**, not fuzzy. Unknown User-Agents pass through.
- **Do not block based on behavioral signals alone** -- they supplement User-Agent detection, not replace it.

## Rate Limiting

The edge function should rate limit at two levels:

**Level 1: Per-IP rate limiting on protected path 403 responses**

If the same IP is generating more than N 403 responses per minute on protected paths, drop to a synthetic `429 Too Many Requests` instead of the informative 403. This prevents:
- DoS via 403 generation (each 403 includes a JSON body).
- Enumeration attacks (scanning all protected paths).

Target: **100 requests/minute per IP** before throttling.

**Level 2: Per-IP rate limiting on fora.json**

fora.json is cacheable, but an aggressive agent might poll it. Rate limit to **10 requests/minute per IP** and rely on `Cache-Control` for normal operation. This is a platform rule in front of the edge function, which only forwards the path to the origin. An Exchange reads the file at registration, on every check of a domain being verified and at every catalog push, so keep the limit above that rate.

Rate limiting implementation:
- **Cloudflare**: Use `request.cf.botManagement` and Cloudflare Rate Limiting rules (not in Worker code -- use platform rate limiting for efficiency).
- **CloudFront**: AWS WAF rate-based rules on the distribution.
- **Akamai**: Rate control via Property Manager.
- **Fastly**: Use `req.http.Fastly-Client-IP` with in-memory counters in the Compute service, or Fastly rate limiting product.

## Bot Pattern Updates

The FORA project should maintain a community-curated bot pattern list as a JSON file at a well-known URL (e.g., `https://fora-protocol.org/bot-patterns.json`). Edge functions can periodically fetch updates from this list. The fetch happens on a timer (hourly), not per-request.
