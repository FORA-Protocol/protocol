## Multi-Source Merge

All sources produce `RawEntry` structs. The Normalizer converts these into a common `CatalogEntry` representation, resolving conflicts when multiple sources provide data for the same URL path.

Higher-priority sources override lower-priority sources for the same path. Fields from higher-priority sources take precedence using a first-non-zero-value-wins strategy.

```go
var sourceOrder = map[IngestionSource]int{
    IngestionSourceFORASitemap: 1,
    IngestionSourceRSL:          2,
    IngestionSourceSitemap:      3,
    IngestionSourceHTMLCrawl:    4,
    IngestionSourceCMSAPI:       5,
    IngestionSourceManual:       6,
}
```

## CatalogEntry: The Universal Representation

```go
type CatalogEntry struct {
    // Identity
    TenantID        string
    Domain          string
    Path            string
    URL             string
    ContentID       string
    Title           string

    // Content metrics
    WordCount       int
    EstimatedTokens int // the resource's size in tokens: the unit_cost denominator, never an estimate on the offer

    // Pricing (authoritative source: Exchange config DB;
    //          fallback: RSL/sitemap hints)
    PricingModel      PricingModel
    Rate              string // exact decimal, e.g. "0.05"
    Currency          string
    Unit              string // the metering unit of a PER_UNIT price
    EstimatedQuantity int32  // the publisher's own estimate, in Unit; 0 when it states none

    // Access control (from RSL permits/prohibits)
    Permissions     []comp.Function
    Prohibitions    []comp.Function

    // Metadata
    Authors         []string
    PubDate         string
    SourceType      int32
    ContentType     comp.ContentType

    // Content identity
    ContentHash string
    HashMethod  string

    // Freshness
    LastModified    time.Time
    Source          IngestionSource
    Freshness       time.Time
    IsGlobPattern   bool
}
```

## Normalizer

The `Normalizer` groups entries by path, sorts by source priority, and overlays fields so that the highest-priority non-zero value wins for each field.

```go
type Normalizer struct {
    logger *slog.Logger
}

func (n *Normalizer) Normalize(
    tenant *TenantConfig,
    sourceEntries map[IngestionSource][]RawEntry,
) []CatalogEntry {
    // Group entries by path
    pathEntries := make(map[string][]RawEntry)
    for _, entries := range sourceEntries {
        for _, entry := range entries {
            pathEntries[entry.Path] = append(pathEntries[entry.Path], entry)
        }
    }

    var catalog []CatalogEntry
    for path, entries := range pathEntries {
        merged := n.mergeEntries(tenant, path, entries)
        catalog = append(catalog, merged)
    }
    return catalog
}
```

The merge strategy for each field:

- **Title**: first non-empty value from highest-priority source
- **WordCount / Tokens**: first non-zero value
- **ContentID**: first non-empty value
- **PricingModel**: first non-unspecified value (along with rate and currency)
- **Permissions / Prohibitions**: first non-empty slice
- **LastModified**: first non-zero time
- **Authors / PubDate**: first non-empty values

Tenant defaults fill in any remaining gaps:

```go
if result.PricingModel == PricingModelUnspecified {
    result.PricingModel = tenant.DefaultPricingModel
    result.Rate = tenant.DefaultRate
    result.Currency = tenant.DefaultCurrency
}
if result.Currency == "" {
    result.Currency = "USD"
}
```

Pricing from public sources (RSL/sitemap hints) or tenant defaults is preliminary. The Pricer stage (Stage 4) overrides with authoritative private pricing.

## Content Extraction via Readability

For URLs without token estimates from higher-priority sources, the pipeline crawls the page and extracts main content using a readability algorithm (Go port of Mozilla's Readability.js).

The extraction flow:
1. Check robots.txt (cached per domain)
2. Rate limit (1 req/sec per domain)
3. Fetch page with `FORA-Exchange/1.0 (content-indexer)` user agent
4. Extract text using readability algorithm
5. Count words and estimate tokens

```go
func (s *HTMLCrawlSource) EnrichEntry(
    ctx context.Context, entry *CatalogEntry,
) error {
    if !s.isAllowed(entry.Domain, entry.Path) {
        return fmt.Errorf("blocked by robots.txt: %s%s", entry.Domain, entry.Path)
    }

    if err := s.rateLimiter.Wait(ctx); err != nil {
        return fmt.Errorf("rate limit wait: %w", err)
    }

    // Fetch and extract
    article, err := readability.FromReader(resp.Body, parsedURL)
    if err != nil {
        return fmt.Errorf("readability extraction: %w", err)
    }

    wordCount := countWords(article.TextContent)
    entry.WordCount = wordCount
    entry.EstimatedTokens = estimateTokens(wordCount)
    entry.Title = article.Title
    return nil
}
```

## Token Estimation

The pipeline estimates each resource's size in tokens. That size is a sizing input for comparison, and nothing more:

- **It is the denominator of unit_cost.** `unit_cost` is the price of one purchase divided by the size of the resource in the comparison unit, tokens for text (see [unit_cost: Normalized Pricing](/getting-started/how-money-flows/#unit_cost-normalized-pricing)). The Exchange uses it to rank offers for an agent request, and agents and Brokers use it to compare offers across providers and Exchanges. It appears on offers and invoices as a reference metric, analogous to eCPM on programmatic ad invoices.
- **It is never an offer's `estimated_quantity`.** `Pricing.estimated_quantity` is only what the publisher states — on a term's pricing, or once for the resource on `ResourceEntry.estimated_quantity` — counted in the price's own `unit`, and the Exchange carries it onto the offer unchanged. The pipeline does not invent one, and a price per access has an estimate in accesses, never a token count.
- **The charged amount follows the offer's pricing, not unit_cost.** A `FLAT` price is charged as stated. A `PER_UNIT` purchase charges the offer's estimate × rate, or one unit's rate when the offer states no estimate, and that charge is final (see [Charging a metered purchase](/protocol/transaction-flow/#charging-a-metered-purchase)).

### Estimation Methods (Priority Order)

| Method | Source | Formula | Accuracy |
|---|---|---|---|
| Provider-provided tokens | FORA sitemap `fora:tokens` | Direct value | Best (provider knows their tokenizer) |
| Provider-provided word count | FORA sitemap `fora:wordcount`, CoMP `text.wordcount`, RSL metadata | `tokens = wordcount * 1.32` | Good (+/-10%) |
| HTML crawl extraction | Readability algorithm on fetched page | Extract text -> count words -> `* 1.32` | Good (+/-15%) |
| CMS API word count | WordPress content field, Ghost html field | Strip HTML -> count words -> `* 1.32` | Good (+/-10%) |
| Tenant default | Manual config | Configured average word count -> `* 1.32` | Rough (+/-30%) |
| Content-length heuristic | HTTP `Content-Length` header | `wordcount = content_length_bytes / 5.5` -> `* 1.32` | Rough (+/-40%) |

### The 1.32 Multiplier

```
estimated_tokens = word_count * 1.32
```

The 1.32 multiplier is derived from empirical analysis of English-language web content across BPE-based tokenizers (GPT-4, Claude). It accounts for subword tokenization splitting longer words into multiple tokens, punctuation and whitespace tokens, and HTML entity remnants after text extraction.

For non-English content, the multiplier varies:

| Language | Multiplier | Notes |
|---|---|---|
| English | 1.32 | Baseline |
| German | 1.45 | Longer compound words |
| Chinese/Japanese | 2.0-3.0 | Character-based, higher token density |
| Arabic/Hebrew | 1.5 | Morphological complexity |

Tenant config can override the multiplier per domain.

### Accuracy of the Estimate

The estimate only sizes a resource for comparison, so an error in it moves `unit_cost`, never a charge:

1. unit_cost is a reference metric for offer construction and comparison, not a billing metric.
2. The charge follows the offer's pricing: a `FLAT` price as stated, and a `PER_UNIT` purchase the estimate × rate the offer states, or one unit's rate without an estimate. That charge is final.
3. A usage report records the quantity consumed and is never refused for its quantity. A disagreement about the quantity consumed is a dispute.

## Deduplication

Deduplication is path-based. When multiple sources provide data for the same URL path, the Normalizer's merge strategy resolves them:

1. Group all entries by their `Path` field
2. Sort entries within each group by source priority (ascending = higher priority first)
3. Overlay fields using first-non-zero-value-wins
4. Produce a single `CatalogEntry` per unique path

Glob patterns (e.g., `/premium/*`) are detected via `strings.ContainsAny(path, "*?[")` and marked with `IsGlobPattern = true` for special handling during catalog compilation.

Content identity via `ContentID` (provider-assigned stable identifier) survives URL changes. When a provider moves content from `/articles/123` to `/premium/123`, the same `ContentID` links both URLs to the same logical content.
