The Exchange charges each purchase to the agent's account at that Exchange. The protocol defines what a purchase costs, and it leaves settlement outside the protocol (see [How Money Flows](/getting-started/how-money-flows/)). Inside FORA Server's Exchange, every charge goes through one Go interface, the billing adapter. The adapter is the only part of the Exchange that talks to a ledger.

FORA Server includes three adapters, and `FORA_BILLING_ADAPTER` selects one at boot.

## Adapter contract

The interface is `billing.Adapter`, in the `src/exchange/internal/billing/adapter.go` file in the FORA Server repository. The adapter represents money as an exact decimal, never as a floating-point number:

```go
// Amount is an exact decimal value in one currency.
type Amount struct {
	Value    *big.Rat
	Currency string
}

type AuthorizeRequest struct {
	TenantID        string
	BillingRef      string // the agent's account, from Register
	UnitCost        Amount
	Quantity        int64  // the offer's estimated quantity, at least 1
	Unit            string // for example "tokens"
	IdempotencyKey  string
	ResourceOwnerID string // the payee
	FeeRateBps      int    // the Exchange's fee, in basis points
}

type AuthorizeResult struct {
	BillingID string
	Approved  bool
	Reason    string // set when Approved is false
}

type Adapter interface {
	EnsureAgentAccount(ctx context.Context, billingRef string) error
	Credit(ctx context.Context, billingRef string, amount Amount, idempotencyKey string) error
	Authorize(ctx context.Context, req AuthorizeRequest) (AuthorizeResult, error)
	Record(ctx context.Context, billingID string, advisoryQuantity int64, idempotencyKey string) error
	Release(ctx context.Context, billingID string, idempotencyKey string) error
	Refund(ctx context.Context, billingID string, amount Amount, reason string, idempotencyKey string) error
	GetBalance(ctx context.Context, billingRef, currency string) (Amount, error)
	AvailableBalance(ctx context.Context, billingRef, currency string) (Amount, error)
	GetQuota(ctx context.Context, billingRef string) (int64, error)
}
```

The following list describes each method:

- `EnsureAgentAccount` opens the ledger account for a `billing_ref`, and leaves an existing account unchanged. The Exchange calls it on the first `Register`.
- `Credit` adds funds outside any purchase. The first credit with a given key wins. The Exchange calls it on the first `Register`, for the welcome credit.
- `Authorize` reserves the charge and returns a `billing_id`. The Exchange calls it for each paid item of a purchase.
- `Record` confirms the reservation. The settled amount is the reserved amount, and the quantity is for information only. The Exchange calls it after it commits the purchase.
- `Release` cancels a reservation that was not consumed. The Exchange calls it when a purchase fails after `Authorize`.
- `Refund` reverses a recorded charge, in part or in full.
- `GetBalance` returns the settled balance in one currency.
- `AvailableBalance` returns what the account can spend in one currency: credits, minus charges, minus open reservations. `GetAccountStatus` calls it to fill `balances`.
- `GetQuota` returns the remaining unit quota.

The Exchange treats each adapter call as one atomic operation, and does not retry it. Each adapter handles its own idempotency: a repeated call with the same key has no further effect. The shared test `TestAdapterConformance` defines the behavior that every adapter that holds balances must have.

## Ledgers

FORA Server includes the following ledgers, and `FORA_BILLING_ADAPTER` selects one of them:

- `free` (default) approves every charge and records nothing. It reports no balance, so `GetAccountStatus` returns none. The transaction log is the only record of a sale.
- `inmemory` keeps prepaid balances in process memory, in USD only. `EXCHANGE_BILLING_SEED` sets the starting balances. A restart loses every balance.
- `tigerbeetle` keeps prepaid balances in a [TigerBeetle](https://github.com/tigerbeetle/tigerbeetle) cluster, with one ledger for each currency in `EXCHANGE_BILLING_LEDGER`. It supports EUR and USD.

If the value is unknown, the Exchange logs a warning and uses `free`. If `tigerbeetle` is selected and the Exchange cannot reach the ledger at boot, the Exchange does not start. The [billing section of the configuration reference](https://github.com/FORA-Protocol/reference-implementation/blob/main/src/exchange/CONFIGURATION.md#25-billing) lists every billing variable, with its format and its default.

With `tigerbeetle`, a charge is a two-phase transfer. `Authorize` creates a pending transfer from the agent's account, `Record` posts it, and `Release` voids it. A pending transfer that nobody posts or voids expires by itself, and the funds return to the agent. The timeout is the delivery URL's lifetime (5 minutes) plus `EXCHANGE_BILLING_HOLD_GRACE` (1 minute by default).

The adapter interface is internal to FORA Server, so the Exchange has no plug-ins. Another ledger is another implementation of `billing.Adapter` in the source code, wired as a new `FORA_BILLING_ADAPTER` value. The wiring also names the currencies that the ledger bills in. Run the shared test `TestAdapterConformance` against the new adapter. An adapter whose ledger keeps a settlement history can also implement `RevenueReporter`, which serves the revenue totals (see [Fees and publisher revenue](#fees-and-publisher-revenue)).

## Currencies

Each offer states its price in one currency, and the Exchange charges the item in that currency. The Exchange converts nothing between currencies.

With `tigerbeetle`, each agent has one balance for each currency that the ledger bills in. The ledger takes a charge from the balance in the offer's currency, and `GetAccountStatus` returns the available balance in each currency.

With `inmemory` or `tigerbeetle`, the ledger refuses an item whose offer is priced in a currency that it does not bill in.

## Identifiers

- **`billing_ref`** is the agent's account. The Exchange creates it on the agent's first `Register`, and returns it in `RegisterResponse`. The Exchange stores it with the agent. The Exchange always reads it from there, by the identity that the request signature proves, and never from the request body.
- **`billing_id`** identifies the reservation that `Authorize` returns for one item. It does not identify the account. The Exchange returns it on the item's `TransactionResultItem`, and stores it with the transaction. `Record`, `Release`, `Refund`, and the agent's usage report use it. A `billing_id` repeats only for a retry of the same reservation. A free item has no reservation and no `billing_id`.
- **`transaction_id`** identifies one purchased item. The Exchange creates it, and does not pass it to the adapter.
- **The idempotency key** for an item is the request's `idempotency_key`, a colon, and the item's `offer_id`. `Authorize`, `Record`, and `Release` for that item use the same key, so a retried purchase never reserves or settles twice.
- **The payee** is the `resource_owner_id` of the resource's catalog entry, as the publisher's site attests it.

## Charging flow

For each item of an `ExecuteTransaction`, the Exchange first verifies the offer and the agent's acceptance. Then it charges the item in the following steps:

1. **Fee rate.** The Exchange reads its fee rate for the item's publisher, `fee_rate_bps` on the seat.
2. **Price.** The Exchange reads the price from the signed offer. The unit cost is the offer's `unit_cost`, or its `rate` when `unit_cost` is not set. The quantity is the offer's `estimated_quantity`, or 1 when the offer states none.
3. **Free items.** When the unit cost is 0, the item skips billing, even when the offer's `rate` is not 0. The Exchange calls neither `Authorize` nor `Record`, and the item has no `billing_id`.
4. **Account.** A paid item needs a registered account. Otherwise, the Exchange denies the item with `DENIAL_REASON_ACCOUNT_NOT_REGISTERED`. If the account registry marks the account inactive, the Exchange denies the item with `DENIAL_REASON_ACCOUNT_INACTIVE`.
5. **Reservation.** `Authorize` reserves the unit cost × the quantity, in the offer's currency, with the payee and the fee rate. If the ledger refuses, the Exchange denies the item with `DENIAL_REASON_INSUFFICIENT_BALANCE`.
6. **Delivery.** The Exchange signs the delivery URL and commits the transaction. If either step fails, the Exchange calls `Release`.
7. **Settlement.** After the commit, `Record` confirms the reservation. With `tigerbeetle`, the ledger splits the charge at this point between the operator and the publisher (see [Fees and publisher revenue](#fees-and-publisher-revenue)).

The item's `cost` in the response is the same unit cost × quantity.

`ReportUsage` moves no money, because the charge is final at purchase. `Register` calls `EnsureAgentAccount`. For an active account, `Register` then calls `Credit` once for each currency in `EXCHANGE_DEFAULT_AGENT_CREDIT`.

## Free and subscription items

A free item is still a purchase. The Exchange skips the ledger, but it signs the delivery URL and writes the transaction as for a paid item. A free item needs no account. The agent still owes a usage report unless the price's metering is `PRICING_METERING_NONE`, and a report on a free item carries no `billing_id`.

A subscription uses this path. In the protocol, a subscription is a free license term behind a concrete subscription scope, and the agent pays for the subscription itself outside the protocol. The Exchange sells such a term only when the request's delegation verifies, and the purchase never reaches the ledger. See [Subscription Billing](/getting-started/how-money-flows/#subscription-billing).

## Fees and publisher revenue

The operator's fee is `fee_rate_bps`, in basis points of the charge. The operator sets it with `AdminService.SetTenantFeeRate` on the admin listener. The value is from 0 to 9999, so 1500 is 15%. The rate applies immediately, without a restart. A reservation keeps the rate that was in effect when the Exchange made the reservation.

With `tigerbeetle`, the ledger splits each charge when `Record` confirms it. The fee is the charge × `fee_rate_bps` / 10000, rounded down, and it goes to the operator's fee account. The rest goes to the publisher's revenue account. The `free` and `inmemory` ledgers do not split.

The publisher console, when the operator runs one, reads a publisher's revenue totals from the Exchange. The totals show the gross, the fee, and the net for a period, in one currency. The totals come from the same ledger that settled the charges, so only `tigerbeetle` reports them. The `free` ledger has no settlements to report, and the `inmemory` ledger keeps no settlement history.

The ledger only records what each publisher earned. Paying the publisher is outside the protocol (see [How Money Flows](/getting-started/how-money-flows/)).

## Failure handling

An adapter reports a refusal in one of two ways:

- A soft refusal is `Approved = false` from `Authorize`, for example for an insufficient balance or an unknown account. The Exchange denies the item in the response body with `DENIAL_REASON_INSUFFICIENT_BALANCE`, whatever the reason. The other items of the request continue.
- Every other failure is an error value. An error for an insufficient balance denies only the item, like a soft refusal. Any other error fails the whole request.

The Exchange does not retry an adapter call. When the Exchange cannot reach the ledger, `/readyz` answers `503`, and `/healthz` stays `200`.

`Record` is best effort. When `Record` fails, the purchase still succeeds, and the Exchange logs `billing_record_failed_best_effort`. The charge is then not settled, and nothing repairs it automatically. With `tigerbeetle`, the reservation expires, and the agent is not charged. The Exchange logs a failed `Release` as `release_hold_failed`. With `tigerbeetle`, that reservation also expires. To find charges that are not settled, see the [troubleshooting section of the runbook](https://github.com/FORA-Protocol/reference-implementation/blob/main/src/exchange/RUNBOOK.md#3-troubleshooting).
