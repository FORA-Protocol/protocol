> Definitive walkthrough of FORA v1.0 as of March 2026. Every field name, signature algorithm, and endpoint matches the current `fora.proto`.

## Scenario

**Agent**: Acme AI's assistant (`acme-ai.example`), running the FORA Agent SDK
**Broker**: Acme AI's hosted Broker (`broker.acme-ai.example`)
**Subscription**: Acme AI has an annual deal with The Daily Meridian via Exchange Alpha
**Request**: The assistant needs an article about AI regulation originally published by The Daily Meridian (`dailymeridian.example`), syndicated to The Harbor Ledger (`harborledger.example`) via Exchange Beta
**Extension Profiles**: Both Exchanges declare `supported_profiles: ["fora-news-v1"]` in their manifests. The Broker forwards `supported_profiles` from the agent to enable profile-aware metadata in offers (e.g., `news.iptc_guid`, `news.correction_status`).

## Phase 0: Provider Setup

Before any agent request, providers configure their domains and Exchanges ingest content into catalogs.

### 0a. The Daily Meridian — RSL + fora.json

**RSL license** — declares licensing terms and a rate of $0.08 per crawl, which The Daily Meridian treats as the most any Exchange may charge for this content. The provider keeps it at `/rsl.txt`, which the edge function passes through, and names it in `robots.txt` with a `License:` line:

```xml
<!-- GET /rsl.txt -->
<rsl xmlns="https://rslstandard.org/rsl">
  <content url="/premium/*">
    <license>
      <permits type="usage">ai-input ai-index search</permits>
      <prohibits type="usage">ai-train</prohibits>
      <payment type="crawl">
        <amount currency="USD">0.08</amount>
      </payment>
    </license>
  </content>
</rsl>
```

**fora.json** — declares which Exchange is authorized to transact:

```json
// GET https://dailymeridian.example/.well-known/fora.json
{
  "ver": "1.0",
  "provider": "dailymeridian.example",
  "contact": "licensing@dailymeridian.example",
  "exchanges": [
    {
      "domain": "exchange.alpha.example",
      "endpoint": "https://exchange.alpha.example/fora/v1",
      "relationship": "PROVIDER_RELATIONSHIP_DIRECT"
    }
  ]
}
```

**Edge function** — deployed on The Daily Meridian's CDN (Cloudflare/Fastly/Lambda@Edge). Blocks unauthorized AI bots with 403, an `X-Content-Rules` header pointing to the provider's own `fora.json`, and an `X-FORA-Exchange` header naming the Exchange that sells the content. Verifies Ed25519 signed URLs for authorized requests, using the Exchange's published public key.

### 0c. Exchange Alpha Resource Ingestion

Exchange Alpha's Resource Ingestion Pipeline runs in the background:

```
1. Crawl dailymeridian.example/sitemap.xml -> discover all /premium/* URLs
2. Fetch the RSL license robots.txt names -> extract permits/prohibits and its rate ($0.08/crawl), The Daily Meridian's cap
3. HTML crawl via readability -> extract text -> word count -> estimate tokens
4. Apply The Daily Meridian's private pricing (from Exchange Alpha config DB): $0.05/article
   (Below the RSL ceiling of $0.08 — compliant)
5. Third-party attestation (Sablecheck via CatalogService.PushResources):
   Sablecheck crawls the article, signs attestation claims with Ed25519:
   { verifier: "sablecheck.example", claims: { estimated_quantity: 3300, word_count: 2500,
     language: "en", iab_categories: ["IAB19-6"] }, signature: "..." }
   Exchange validates: sablecheck.example is in dailymeridian.example's catalog_contributors,
   verifies signature against the key in sablecheck.example's WBA directory
   (the JWK Set at sablecheck.example/.well-known/http-message-signatures-directory),
   selected by the attestation's keyid (RFC 7638 thumbprint)
6. Build catalog entry:
   {
     domain: "dailymeridian.example",
     path: "/premium/ai-regulation-2026.html",
     title: "AI Regulation: What Providers Need to Know",
     word_count: 2500,
     estimated_quantity: 1,   // in the price's unit: one access per purchase
     pricing: { model: PRICING_MODEL_PER_UNIT, rate: "0.05", currency: "USD", unit: "accesses", unit_cost: "0.00001515" },
     // unit_cost = $0.05 / 3300 tokens (the article's attested size), for comparison only
     identity: {
       canonical_url: "https://dailymeridian.example/premium/ai-regulation-2026.html",
       iptc_guid: "urn:newsml:dailymeridian.example:20260315:ai-reg-001",
       content_hash: "a1b2c3d4e5f6...",
       hash_method: "simhash-v1",
       resource_mutability: RESOURCE_MUTABILITY_STATIC
     },
     attestations: [
       { verifier: "sablecheck.example", keyid: "kPrK_qmxVWaYVA9wwBF6Iuo3vVzz7TxHCTwXBygrS4k",
         attested_at: "2026-03-14T09:00:00Z",
         uri: "https://dailymeridian.example/premium/ai-regulation-2026.html",
         claims: { estimated_quantity: 3300, word_count: 2500, language: "en" },
         signature: "base64-ed25519-sablecheck..." }
     ],
     terms: [
       { semantics: TERM_SEMANTICS_ENUMERATED,
         pricing: { model: PRICING_MODEL_PER_UNIT, rate: "0.05", currency: "USD", unit: "accesses" },
         restrictions: [
           { kind: RESTRICTION_KIND_FUNCTION,
             permitted: ["ai-input", "ai-index", "search"],
             prohibited: ["ai-train"] }
         ] }
     ]
   }
7. Compile into radix trie -> serialize to catalog.bin -> Exchange loads via atomic pointer swap
```

Exchange Alpha also knows about Acme AI's subscription, looked up by Acme AI's account handle (minted at registration):

```
BillingAdapter.CheckSubscription("acct_7f3e21c9", "daily-meridian")
  -> { subscription_id: "SUB-ACME-MERIDIAN-2026", active: true, quota_remaining: 850000 }
```

## Phase 1: Agent Request (SDK with Ed25519 Signing)

The assistant is answering a user question about AI regulation. The SDK triggers:

```go
results, err := client.FetchBatch(ctx, []string{
    "https://dailymeridian.example/premium/ai-regulation-2026.html",
})
```

Inside the SDK:

```
Step 1: Parse domain -> "dailymeridian.example"

Step 2: ExchangeRegistry lookup
  - Cache miss for dailymeridian.example
  - Background: fetch https://dailymeridian.example/.well-known/fora.json
  - Discovers: exchange.alpha.example is authorized (PROVIDER_RELATIONSHIP_DIRECT)
  - Caches: dailymeridian.example -> [exchange.alpha.example]

Step 3: Prepare RFC 9421 HTTP Message Signature (alg=ed25519)
  - requester.id = "acme-agent-001"
  - requester.domain = "acme-ai.example"
  - Sign the HTTP request per RFC 9421 under the Web Bot Auth profile: the
    SDK adds Content-Digest, an empty Authorization, Signature-Agent
    (sig1="https://acme-ai.example"), Signature-Input and Signature. The signature
    covers @method, @target-uri, content-digest, authorization and
    "signature-agent";key="sig1", with created, expires, keyid, nonce and
    tag="web-bot-auth"
  - Authentication is asymmetric:
    the agent signs with its Ed25519 private key (never leaves the agent),
    the Exchange verifies with the public key fetched from the WBA
    directory at acme-ai.example/.well-known/http-message-signatures-directory
```

**Key insight**: The SDK discovers Exchanges from the provider's `fora.json`. It only finds the authorized Exchange for THAT domain. Cross-provider discovery (same article on different domains) requires either a hosted Broker that has crawled multiple providers' `fora.json`, or the agent explicitly requesting multiple URLs across providers.

## Phase 2b: Cross-Provider via Broker (Broker-Signed Queries, OfferGroups, SimHash)

If Acme AI uses its hosted Broker instead of the SDK directly, the Broker provides cross-provider intelligence. The agent sends a `DiscoveryRequest` to the Broker with multiple URIs (`BrokerService.Resolve` is discovery-only — it returns offers grouped by URI; execution happens later via a separate `ExecuteTransaction` call). Agent → Broker:

{/* fora-validate: DiscoveryRequest */}
```json
{
  "ver": "1.0",
  "requester": {
    "id": "acme-agent-001",
    "domain": "acme-ai.example",
    "type": "REQUESTER_TYPE_AGENT",
    "scopes": ["*"]
  },
  "uris": [
    "https://dailymeridian.example/premium/ai-regulation-2026.html",
    "https://harborledger.example/premium/ai-regulation-republish.html"
  ],
  "acceptable_restrictions": [{ "axis": "RESTRICTION_KIND_FUNCTION", "values": ["ai-input"] }],
  "constraints": {
    "preferred_exchanges": ["exchange.alpha.example"],
    "max_unit_cost": "0.00005",
    "reporting_capable": true,
    "budget_scope": "team:acme-rag",
    "period_budget": { "amount": "500.00", "currency": "USD" },
    "budget_period": "2592000s"
  }
}
```

### Broker Fans Out with Its Own Signed Queries

Discovery through the Broker is Broker-led: the agent asked the Broker, and the Broker chooses which Exchanges to query. For each Exchange, the Broker originates its own query (here it batches the URIs and sets its own `deadline`) and:
1. Carries the agent's `requester` message, naming as `requester.domain` the host of the directory the agent's signature verified against (`acme-ai.example`, as the agent sent it)
2. Signs the query alone, with its own labeled RFC 9421 HTTP Message Signature covering its own request components and only its own `Signature-Agent` member. The query carries no agent signature headers

Broker → Exchange Alpha (multi-URI batch query) — `POST https://exchange.alpha.example/fora/v1/fora.v1.ExchangeService/DiscoverResources`:

{/* fora-validate: ResourceQuery */}
```json
{
  "ver": "1.0",
  "exchange": "exchange.alpha.example",
  "requester": {
    "id": "acme-agent-001",
    "domain": "acme-ai.example",
    "type": "REQUESTER_TYPE_AGENT",
    "scopes": ["*"]
  },
  "uris": [
    "https://dailymeridian.example/premium/ai-regulation-2026.html",
    "https://harborledger.example/premium/ai-regulation-republish.html"
  ],
  "acceptable_restrictions": [{ "axis": "RESTRICTION_KIND_FUNCTION", "values": ["ai-input"] }],
  "deadline": "0.4s"
}
```

Exchange Alpha verifies the Broker's signature -- it looks up the public key by its `keyid` thumbprint in the key directory named by the Broker's `Signature-Agent` member, Ed25519 verifies, and authenticates the caller as the Broker. The query carries no delegation, and the Exchange would not honour one: nothing on a query the Broker signs alone can pass its holder binding. How an agent proves a holder-of-key entitlement at discovery time through a Broker is an open protocol question. A discovery query moves no money, so it carries no agent consent; see [Multi-hop forwarding](/protocol/authentication/#multi-hop-forwarding).

### Content Deduplication: IPTC GUID + SimHash Fallback

The Broker groups offers by content identity:

```
Step 1: Group by iptc_guid
  - iptc_guid "urn:newsml:dailymeridian.example:20260315:ai-reg-001" matches across all 3 offers
  - These are ALL the same underlying article (Daily Meridian original, syndicated to The Harbor Ledger)

Step 2: SimHash cross-check (for non-news content without IPTC guids)
  - Exchange Alpha hash: "a1b2c3d4e5f6..." (simhash-v1)
  - Exchange Beta hash:  "a1b2c3d4e5f7..." (simhash-v1)
  - Hamming distance = 1 bit -> substantially similar (threshold < 3 bits)
  - For 99% of web content that lacks IPTC guids, SimHash is the primary dedup signal.
    The Exchange computes SimHash during ingestion from extracted article text.
    The Broker groups by SimHash similarity (Hamming distance).
    This is approximate but catches obvious syndication and republication.
```

### Broker Selection Engine

```
Step 3: Order within the content group
  The Broker keeps all three offers, each as the full package its Exchange
  signed, and puts them in its order of relevance. The agent named Exchange Alpha
  in preferred_exchanges, so Exchange Alpha's offers come first:
  1. 4f155204-a53e-42aa-8471-154f87d7d3d5 ($0, subscription, Exchange Alpha, attested by sablecheck.example)

Step 4: Budget filter (applied before the offers are returned)
  - Spend so far for scope "team:acme-rag", as this Broker counts it: $142.50
    of the $500.00 period budget. Resolve never charges.

    come back with OFFER_ABSENCE_REASON_BUDGET_EXCEEDED (a "no result", not an error).

### The Agent Chooses

The agent gets all three offers and decides by its own policy: use its subscription where it covers the content, and prefer third-party attested content. It chooses `4f155204-a53e-42aa-8471-154f87d7d3d5`, the subscription offer from Exchange Alpha, at zero marginal cost and attested by sablecheck.example.

## Phase 4: Content Fetch (Ed25519 Signed URL, Agent Identity Binding)

```
Agent -> CDN: GET https://cdn.dailymeridian.example/server/premium/ai-regulation-2026.html
              ?agent_id=NzbLsXh8...
              &exp=1710517800
              &kid=vJ3xR1mQ...
              &sig=k7Qm2xR9vT4nB8aL...
              Header: X-FORA-Agent-Key: <agent public key, base64url>
              Header: Signature-Agent: sig1="https://acme-ai.example"
              Header: Signature-Input: sig1=("@method" "@target-uri" "signature-agent";key="sig1");created=...;expires=...;keyid=...;alg="ed25519";nonce=...;tag="web-bot-auth"
              Header: Signature: sig1=:<standard base64>:

Edge Function:
  1. Has a sig param? YES
  2. Resolve kid to a public key from the Exchange key directory (cached)
  3. Verify the Ed25519 signature over "GET\n<URL without sig, query sorted>" -> PASS
  4. Check expiry: exp > now? -> PASS (URL valid for 5 minutes)
  5. Check agent identity binding:
     thumbprint(presented public key) == agent_id == keyid? -> PASS
     Verify the Web Bot Auth signature with that key (proof of possession) -> PASS
     (The agent must hold the private half; presenting the public key is not enough)
  6. Strip agent_id, exp, kid, sig -> CDN serves content from S3/origin

CDN access log records:
  - URL with all params (agent_id, exp, kid, sig)
  - Client IP, timestamp, bytes transferred, HTTP 200
  - This log is controlled by the provider (The Daily Meridian) and used for reconciliation
```

**Canonical message**: the literal `GET`, one newline, then the whole URL with the `sig` parameter removed and the remaining query sorted by key — so scheme, host, path and every other parameter are covered. The delivery-URL signature and the offer signature are both Ed25519; they use different keys and are verified by different parties. See [Signed URL Verification](/components/edge-function/signed-url-verification).

## Phase 7: Dispute Resolution (v1.0 -- When Things Go Wrong)

If the content delivered by the CDN does not match what was promised in the Offer, the agent can file a dispute. The dispute chain enforces a strict order: the agent MUST have filed a `UsageReport` (Phase 5) before disputing.

### Example: Content Hash Mismatch

```
Agent verifies delivered content:
  1. Compute SimHash of received HTML -> "a1b2c3d4e5f9..."
  2. Compare with Offer's identity.content_hash -> "a1b2c3d4e5f6..."
  3. Hamming distance = 2 bits -> within SimHash tolerance (threshold 3)
  4. No dispute needed (content is substantially similar)

But if Hamming distance > threshold, or content is entirely different:
  Agent files DisputeTransaction
```

### Dispute Request

```json
POST https://exchange.alpha.example/fora/v1/fora.v1.ExchangeService/DisputeTransaction

{
  "ver": "1.0",
  "transaction_id": "txn-alpha-001",
  "billing_id": "bill-sub-alpha-001",
  "report_id": "rpt-001",
  "reason": "DISPUTE_REASON_CONTENT_MISMATCH",
  "description": "Content hash differs from offer: expected a1b2c3d4e5f6, received a1b2c3d4ffff",
  "received_content_hash": "a1b2c3d4ffff...",
  "received_hash_method": "simhash-v1"
}
```

### Dispute Response

```json
{
  "dispute_id": "disp-alpha-001",
  "status": "DISPUTE_STATUS_AUTO_RESOLVED",
  "resolution": "RESOLUTION_TYPE_CREDIT",

The dispute lifecycle progresses through: `FILED` -> `AUTO_RESOLVED` / `EVIDENCE_NEEDED` -> `UNDER_REVIEW` -> `RESOLVED` -> `FINAL`. Appeals re-enter `UNDER_REVIEW`.

## What the Broker Adds (Cross-Provider Intelligence)

**Without Broker (SDK only)**: the agent found the article via Exchange Alpha (from `fora.json`) and got the subscription deal. It never knew The Harbor Ledger also had the article at $0.07 via Exchange Beta.

**With Broker**: the Broker queried both Exchanges, matched the same article via iptc_guid (confirmed by SimHash similarity) and returned every offer with its attestation data. The agent still chose the subscription offer -- but now Acme AI has intelligence:

```
"This article is available from two sources:
  - Exchange Alpha (The Daily Meridian, subscription, $0/request, third-party attested by sablecheck.example)
  - Exchange Beta (The Harbor Ledger, per-request, $0.07/request, third-party attested by sablecheck.example)

Our subscription saves us $0.07 per request from the alternative source.
At 10K requests/month for this provider's content, that's $700/month
in avoided per-request costs — data for the subscription renewal.

Both sources carry Level 2 (third-party) attestations from sablecheck.example.
The Daily Meridian original has higher word_count (2500 vs 2350) — more complete."
```

This is the Broker's value: **every offer for the same content in one answer, each as its Exchange signed it, so the agent decides with the whole picture: market intelligence for subscription negotiations and attestation-aware content selection.**
