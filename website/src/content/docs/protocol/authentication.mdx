## Overview

FORA authentication answers three questions for every request:

1. **Who are you?** — Requester identity, proven by Ed25519 signature over a domain-bound key
2. **What can you access?** — Scopes carried in the request (and optionally in a delegation token)
3. **Who authorized you?** — Delegation chain from a principal (organization, user, upstream agent) via holder-bound JWTs that can be narrowed without round-tripping to the issuer

These three layers are independent. A public agent with no delegation still authenticates (layer 1) and declares scopes (layer 2, defaulting to public access). An enterprise agent adds a delegation token (layer 3) that binds the agent to a principal's entitlements with time and spend limits.

## Requester Identity

Every FORA request carries a `Requester` message that identifies who is making the request.

### Key Lookup

The Exchange resolves a requester's public key by fetching its key directory — the JWK Set at `{origin}/.well-known/http-message-signatures-directory` — and selecting the `JsonWebKey` whose RFC 7638 thumbprint matches the request signature's `keyid`.

The `{origin}` comes from the **`Signature-Agent` header**, not from the `Requester` message and not from the `fora.json` manifest. `Signature-Agent` is a dictionary, and the member the verifier follows is the one the signature itself covers, as `"signature-agent";key="<label>"`. Because that member is signed, the pointer the Exchange follows is one the signer committed to, and an attacker cannot repoint it under a valid signature. This is what makes the lookup meaningful: the `keyid` is only a key thumbprint — proof that the signer holds the key, not a claim about who they are — so it is the directory publishing that key that establishes whose key it is. A verifier therefore keys its lookup on the pair (directory URL, `keyid`), never on the `keyid` alone.

This ties cryptographic identity to DNS ownership — if you control the domain, you control the key. The directory's format, media type and signed response are specified in [Key Directory](#key-directory), with a complete example response.

### The WBA Directory Endpoint

Signing keys are published in a dedicated Web Bot Auth key directory at `/.well-known/http-message-signatures-directory`, separate from the role manifest at `/.well-known/fora.json`. It is served over https, answers `200` with no redirect, and uses the media type `application/http-message-signatures-directory+json`. The body is a JWK Set: a `keys` array of Ed25519 JWKs plus an optional `revocation_url`. Each key is identified by its RFC 7638 thumbprint (the value carried as the RFC 9421 `keyid`), so the directory carries no `kid` labels. Each key carries `alg` `EdDSA`, the JOSE name, which deliberately differs from WG-00 §5.5.1 (see [Key Directory](#key-directory)). The response is signed by each key it lists. Every FORA participant — agent, exchange, broker, publisher — serves one. See [Key Directory](#key-directory) for the full rules.

### Web Bot Auth Conformance

FORA request signatures follow Web Bot Auth (WBA), as specified by the IETF webbotauth working group in [draft-ietf-webbotauth-httpsig-protocol-00](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/00/) (1 September 2026). This page calls that document **WG-00**. It is the only document the working group has adopted, and it replaced the earlier individual architecture and directory drafts. FORA pins to WG-00. The editor's copy after -00 proposes that `Signature-Agent` carry a direct JWK Set URL instead of an origin, so FORA will revisit this profile when -01 is published.

Conformance is a property FORA has to maintain on purpose. It does not follow from sharing RFC 9421 and Ed25519 with WBA: a signature can use both and still be refused by every WBA verifier. Conformance means two things, and FORA requires both:

- **FORA signatures verify as WBA.** Every signature a FORA participant creates is a conformant WG-00 signature. A WBA verifier that knows nothing about FORA can verify it and attribute it to the signer's directory.
- **WBA signatures verify at FORA.** A FORA verifier accepts a signature made by any WBA library, provided the signature also covers the extra components FORA requires on that route. FORA advertises those components through WBA's `Accept-Signature` mechanism, so a WBA library that can add covered components can call FORA without FORA-specific code.

The rules that make both true are in [The Web Bot Auth Profile](#the-web-bot-auth-profile). FORA departs from WG-00 in one deliberate place, stated with its reason where it applies: a key directory's JWK `alg` is the JOSE name `EdDSA` ([Key Directory](#key-directory)). It does not change how a WBA verifier checks a FORA request signature.

WBA establishes identity: this bot is who it claims to be. FORA adds the transaction layer on top of that identity: this bot is authorised to access this content at this price.

:::caution[Profile change in progress]
This profile is the target for the next SDK release. The SDKs released as v1.0.8 do not produce or check it yet. They send `Signature-Agent` as a bare, unquoted URL rather than a dictionary, set no `tag`, generate a 16-byte nonce, and refuse any signature that does not cover all five FORA components. The reference directories are served as `application/jwk-set+json`. The change is a hard cut with no transition window: once the profile ships, verifiers refuse the bare unquoted `Signature-Agent` that v1.0.8 sends, so a v1.0.8 client must upgrade to keep working. The SDKs and the reference implementation change together; the [changelog](/reference/changelog/) lists each difference.
:::

### Signature Verification

The `Requester` message carries identity semantics only — it has **no** signature field. Request authentication is an [RFC 9421 HTTP Message Signature](https://www.rfc-editor.org/rfc/rfc9421) over the HTTP request itself, carried in the `Signature`, `Signature-Input` and `Signature-Agent` HTTP headers rather than in the protobuf body. This separates identity semantics (the `Requester` message) from cryptographic proof (the HTTP signature).

Every signature MUST be a conformant WG-00 signature, as [The Web Bot Auth Profile](#the-web-bot-auth-profile) describes. On a FORA RPC, which carries a body, the signature MUST also cover `@method`, `@target-uri`, `content-digest` and `authorization`. A signature that omits one of them is refused, and the refusal names the missing component. `authorization` is covered even when empty, so a token cannot be slipped under an existing signature. The `Signature-Agent` member is covered so the directory the key is looked up in cannot be repointed.

Covering a header is not the same as sending it, and both are required. A verifier rebuilds the signature base from the request it **received**, so a covered name the request does not carry cannot be reconstructed at all:

- A sender MUST transmit every covered header, **including an empty `Authorization`**. `Authorization:` with an empty value is the ordinary shape of a request from an agent holding no bearer token, and the field line MUST be present. `Signature-Agent` is never empty: it always names the signer's https origin.
- A verifier MUST reject a request that **omits** a covered header, and MUST accept a covered `Authorization` that is **empty**. Treating a missing header as empty invents a value the sender may never have bound, and accepts a request whose base cannot be reconstructed.
- Header field names are case-insensitive, and repeated field lines under one name are joined with `", "` before the base is rebuilt (RFC 9421 §2.1). A second field line placed beside a covered one therefore **changes** that covered value and invalidates the signature — it does not replace or override it. This is the mechanism that stops a token being slipped under an existing signature, and it means a verifier MUST NOT resolve a covered header by picking one field line among several.

The Exchange verifies it by:

1. Parsing `Signature`, `Signature-Input` and `Signature-Agent`, and selecting the `Signature-Agent` member the signature covers
2. Checking the signature against the profile: `tag="web-bot-auth"`, `created`, `expires`, `keyid` and `alg="ed25519"` present, `@target-uri` or `@authority` covered, and on a FORA RPC the four FORA components covered
3. Fetching the key directory at `{origin}/.well-known/http-message-signatures-directory` for the origin that member names, and selecting the `JsonWebKey` whose RFC 7638 thumbprint matches the `keyid` (and whose `[not_before, not_after)` window covers now)
4. Reconstructing the signature base from the declared components and verifying the Ed25519 signature in the `Signature` header against that key
5. Confirming the `Content-Digest` matches the request body, and that the directory that published the key is the identity the caller is authorised as

If verification fails, the Exchange rejects the request. No fallback, no degraded mode. See [The Web Bot Auth Profile](#the-web-bot-auth-profile) below for the header details and a complete example.

## Delegation

The delegation token is a **JWT** (the default and fully-specified format) that is **holder-of-key bound**: the grant is tied to a specific key via the [RFC 7800](https://www.rfc-editor.org/rfc/rfc7800) `cnf` confirmation claim, and the holder proves possession by signing the request with that key (the same RFC 9421 signature it already sends). The token is *not* a bearer credential — copying it is useless without the matching private key.

> **Why not a plain bearer JWT?** A bearer JWT is usable by anyone who holds it, and it can't be narrowed for a sub-agent without a round trip to the issuer. FORA fixes both with one mechanism: `cnf` holder-of-key binding (theft-resistance) plus **chained `cnf` JWTs** (offline delegation). A principal narrows a grant for an agent by issuing a child JWT — no call back to the original issuer.

### Holder-of-key, not bearer

Each delegation JWT carries `cnf.jkt` — the [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638) JWK thumbprint of the key the grant is bound to. At request time the verifier computes the thumbprint of the key that signed the RFC 9421 request and checks it equals `cnf.jkt`. A thief who steals the token but not the private signing key cannot produce a valid request, so the token grants nothing. This is the same proof-of-possession mechanism as DPoP.

### How delegation works

Delegation is a chain of `cnf`-linked JWTs, content owner → principal → agent:

- **Authority JWT** — signed by the **resource owner** (the issuer). Carries the granted `scope`, `exp`, and `cnf.jkt` = the **principal's** key. The owner's public key is the verifier's only trust anchor.
- **Delegation JWT** — signed by the **principal**, narrowing the grant for a specific **agent**: `scope ⊆ parent`, shorter `exp`, `cnf.jkt` = the **agent's** key. It carries the principal's public key in its JOSE header (`jwk`) so the verifier can both link it to the authority's `cnf` and verify it.
- **Request** — signed by the **agent** (RFC 9421); the verifier checks `thumbprint(request key) == delegation cnf.jkt`.

**Chain-linkage invariant:** each JWT's signer MUST be the key the parent named in `cnf`. The owner verifies the authority; `authority.cnf` pins the principal; the delegation's header key must match that pin (and verifies the delegation); `delegation.cnf` pins the agent; the request key must match that pin. A token signed by a key not named upstream is rejected.

The chain narrows only — a child's `scope` must be covered by its parent's (see [Scope Matching](#scope-matching)). The principal can delegate to a sub-agent (and that sub-agent further) by issuing another child JWT, entirely offline. Verifiers need only the **owner's** public key; the principal and agent keys ride inside the chain.

### The Delegation Message

The token is carried in the `Delegation` message, nested inside `Requester`:

| Field | Type | Description |
|---|---|---|
| `principal_domain` | `string` | Who granted this delegation (domain for public key lookup) |
| `principal_id` | `string` | Principal's identifier (e.g., `"user@acme.com"`, `"marketdata.example.com"`) |
| `scopes` | `repeated string` | Scopes granted — convenience mirror of the token's `scope` claim |
| `expires_at` | `Timestamp` | When this delegation expires. Exchange MUST reject expired tokens |
| `max_spend_cents` | `int64` (optional) | Maximum spend in currency minor units (e.g. cents for USD) |
| `token` | `bytes` | Token bytes — a JWT (base64url JWS) by default |
| `token_format` | `string` | Token format: `"jwt"` (the sole/default format) |
| `revocation_uri` | `string` (optional) | URI for real-time revocation checking (high-value transactions) |
| `max_accesses` | `int32` (optional) | Maximum number of accesses allowed under this delegation. Exchange tracks count and denies with `DENIAL_REASON_QUOTA_EXCEEDED` when count >= limit. |
| `quota_period` | `Duration` (optional) | How often access/spend counters reset. E.g., `"2592000s"` (30 days) for monthly subscriptions — proto-JSON encodes `Duration` as seconds. When absent, quota is lifetime (bounded only by `expires_at`). |
| `issuer` | `string` (optional) | Token issuer — OIDC issuer URL (for JWT signature validation via OIDC→JWKS) |
| `ext` | `Struct` | Implementer-specific extensions |
| `ext_critical` | `repeated string` | Critical extension keys (COSE crit pattern) |

The `scopes` field is a convenience mirror — the Exchange MAY use it for fast catalog filtering before performing full token verification. The token's claims are authoritative.

### Delegation-Claims Profile

The `token`'s claims are the **authoritative** source of the grant (the plaintext `Delegation` fields are only the convenience mirror). FORA defines a small **registered claim vocabulary** — the same registered-tokens + optional-fields + vendor-namespace pattern used elsewhere in the protocol:

| Claim | JWT claim | Required? | Meaning |
|---|---|---|---|
| holder | `cnf` (with `jkt`) | **Yes** | Binds the grant to a key by RFC 7638 thumbprint — verified per [Verification](#verification) (request-signing key MUST hash to `cnf.jkt`). Without it the token is bearer-usable. |
| issuer | `iss` | Yes | Who granted it (resource owner / principal). |
| `scope` | `scope` | No | Granted scopes (space-delimited; segment-wise matching — see [Scope Matching](#scope-matching)). |
| `exp` | `exp` | No (recommended) | Expiry. |
| `max_spend_cents` | `fora_max_spend_cents` | No | Spend cap (currency minor units). |
| `max_accesses` | `fora_max_accesses` | No | Access-count cap. |
| `quota_period` | `fora_quota_period` | No | Counter reset period. |

Rules:

- **Everything except the holder binding (`cnf`) is optional.** An issuer that only wants scope + expiry sets just those; absent caps mean "no cap from the delegation" (the Exchange's own limits still apply).
- **Vendors MAY add namespaced claims** (`vendor:claim`).
- **Constraints fail closed.** A claim a verifier cannot evaluate is **binding by default** — it MUST reject rather than ignore (a dropped constraint would fail *open*, granting more than intended). This mirrors [`Restriction.advisory`](/protocol/licensing-terms/): the issuer may mark a custom claim *advisory* to downgrade it to ignorable. (The issuer lists the mandatory-to-understand claims; an unrecognized non-advisory claim is rejected.)
- **`fora_`-prefixed claim names are reserved** for this registry. Vendors MUST use their own `vendor:` namespace and MUST NOT define `fora_*` names, so registered claims can never be shadowed.
- **Claim values keep their home encoding.** RFC-registered claims use the encoding their RFC defines — `exp` is a NumericDate (seconds since epoch, RFC 7519). `fora_*` claims mirror a `Delegation` field and use that field's proto-JSON encoding — for example, `fora_quota_period` is a Duration string in seconds (`"2592000s"`), the same form the [`quota_period` field](/reference/proto-fora/#delegation) carries on the wire.

> **Token format.** The delegation token is a **holder-bound JWT** — `token_format: "jwt"` is the sole format conformant implementations support. Multi-hop attenuation is expressed as a chain of `cnf`-linked child JWTs (each signed by the key its parent named, each narrowing scope), and the holder binding always applies (the request-signing key must match the holder the token is sealed to).

### Delegation chain example

MarketData (resource owner) issues an authority JWT to the Acme principal, bound to Acme's key:

```json
// authority JWT — signed by marketdata.example.com (the owner key)
// header
{ "alg": "EdDSA", "typ": "JWT" }
// claims
{
  "iss": "marketdata.example.com",
  "scope": "quote:* earnings:*",
  "max_spend_cents": 50000,
  "exp": 1781787345,
  "cnf": { "jkt": "<thumbprint of Acme's principal key>" }
}
```

Acme delegates to a research agent that only needs earnings data, narrowing scope and shortening the TTL — no call back to MarketData:

```json
// delegation JWT — signed by Acme's principal key
// header carries the principal pubkey so the verifier links it to authority.cnf
{ "alg": "EdDSA", "typ": "JWT",
  "jwk": { "kty": "OKP", "crv": "Ed25519", "x": "<Acme principal pubkey>" } }
// claims
{
  "iss": "acme",
  "scope": "earnings:*",
  "exp": 1781701545,
  "cnf": { "jkt": "<thumbprint of the agent's key>" }
}
```

The agent then signs its request (RFC 9421) with its own key. **Zero round trips to MarketData** — each delegation is a locally-issued child JWT.

### Verification

The Exchange/edge verifies a delegation by (offline, using only the owner's public key):

1. **Verify the authority JWT** with the resource owner's published key (the trust anchor). Read its `scope`, `exp`, and `cnf.jkt`.
2. **Verify each delegation JWT** with the key in its own JOSE header `jwk` — but only after checking `thumbprint(header key) == parent cnf.jkt` (the **chain-linkage invariant**). Reject a JWT signed by a key the parent did not name. Check each child's `scope` is covered by its parent's.
3. **Verify holder binding** — the key that signed the HTTP request ([RFC 9421](#request-signatures-rfc-9421)) MUST hash to the final delegation's `cnf.jkt`. If not, **reject** (`DENIAL_REASON_DELEGATION_INVALID`). This is what makes a leaked token useless to a thief: possessing the bytes is not enough — you must control the bound private key. It is **not optional** and **not skippable**; an Exchange that omits it reduces the token to a bearer credential and breaks the anti-theft guarantee.
4. Check `exp` on every JWT in the chain against current time.
5. Optionally check `revocation_uri` for high-value transactions.

This is entirely offline — no callback to the issuer. The verifier needs only the owner's published public key (cacheable); the principal and agent keys arrive inside the chain (header `jwk` + `cnf.jkt`).

**Binding across hops.** Each delegation re-binds to the next holder's key (`cnf.jkt` of the child = the next agent), so at every hop the bound key is whoever now signs the request. The chain of JWT signatures carries the binding forward — there is no point at which the token reverts to bearer form.

**Which signature binds in a brokered request.** A forwarded request can carry more than one RFC 9421 signature (the agent's, plus one from each intermediary). The holder-binding check always matches the **terminal holder** — the key named in the *final* delegation's `cnf.jkt`. A relay that forwards the request unchanged forwards the agent's delegation unchanged, the agent remains the terminal holder, and the **agent's** request signature is the one that must match `cnf.jkt` (the relay's signature is provenance only). FORA's Broker re-packages the request and is its wire signer, so the check matches the Broker's key: a delegated request through a Broker requires the agent to have explicitly **delegated to the Broker** (the Broker holds a child JWT bound to its own key), the same rule [Projected execute requests](#projected-execute-requests) states. Intermediaries never silently become the holder.

### Delegation Denial Reasons

When delegation verification fails, the Exchange returns a specific denial reason in the response:

| Denial Reason | Meaning |
|---|---|
| `DENIAL_REASON_QUOTA_EXCEEDED` | Subscription access count exhausted for this period |
| `DENIAL_REASON_DELEGATION_INVALID` | Delegation token missing, unverifiable (broken chain linkage or holder-binding mismatch), expired, or it widens scope beyond its parent |

## Scope-Based Access

Scopes are the mechanism by which the Exchange decides what resources to show a requester. The flow is:

1. Agent sends `ResourceQuery` with `Requester.scopes` (and optionally a `Delegation` that also carries scopes)
2. Exchange filters its catalog — only resources matching the declared scopes are returned
3. Resources outside the scopes are **not returned**. The requester never learns they exist.

### Scope Format

Scopes follow the pattern `{domain}:{permission}` or `{profile}:{permission}`:

| Scope | Meaning |
|---|---|
| `"credit:read"` | Can access credit reports (read-only) |
| `"subscription:marketdata-2026"` | Has active MarketData subscription |
| `"revshare:publisher-x"` | Party to an off-protocol revenue-share agreement (gates the `FREE` revshare term — see [Licensing Terms](/protocol/licensing-terms/#revenue-share-arrangements)) |
| `"academic:*"` | Full access to academic resources |
| `"internal:reports"` | Can access internal reports |
| `"dist:US:CA"` | Multi-segment scope (colon-separated; matched segment-wise, see below) |
| `"*"` | Unrestricted (public Exchange default) |

### Scope Matching

Matching is **segment-wise** (`:`-separated). A granted scope **G** covers a required scope **R** iff, comparing segment by segment, each G segment equals the corresponding R segment **or** is `*`; a **terminal `*` matches all remaining segments**. There is **no implicit prefix match**. A grant that is **more specific than what is required does not cover it** — coverage requires G to be equal-to-or-broader-than R, never narrower (e.g. granted `dist:US:CA` does not cover required `dist:US`).

| Granted | Covers | Does **not** cover |
|---|---|---|
| `dist:*` | `dist:US`, `dist:US:CA` | — |
| `dist:US:*` | `dist:US:CA` | `dist:EU` |
| `dist` | `dist` | `dist:US` |
| `dist:US:CA` | `dist:US:CA` | `dist:US` (grant narrower than required) |
| `*` | everything | — |

### Access Tiers

**No scopes (empty):** Exchange applies its default access policy — typically all publicly available resources. This is the common case for public agents.

**Subscription scopes:** A scope like `subscription:nyt-2026` signals that the requester has a subscription entitlement. The Exchange returns subscription pricing (zero marginal cost) instead of per-request pricing.

**Enterprise scopes:** Specific `{domain}:{permission}` scopes grant access to restricted resources. The Exchange enforces RBAC by filtering the catalog to matching resources.

### Disclosure Policy

When a resource exists but the requester's scopes are insufficient, the Exchange decides how to respond based on its disclosure policy:

- **Hide existence:** Silent omission. The resource is simply not returned — no hint that it exists. Appropriate when the resource's existence is itself sensitive.
- **Reveal it's gated:** Returns `OFFER_ABSENCE_REASON_SCOPE_INSUFFICIENT` in the `OfferGroup.absence_reason` field, telling the requester the resource exists but their scopes/subscription don't cover it. Standard wherever access is subscription- or scope-gated — enterprise RBAC and public marketplace subscriptions alike.

This distinction prevents information leakage on public Exchanges while allowing enterprise environments to provide actionable diagnostics.

## Multi-hop forwarding

When a request passes through a forwarding party (e.g., Agent to Broker to Exchange), nothing about the forwarding is carried in the message body. Each party signs the request it sends with its own labeled [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421) signature in the HTTP headers. This section is the one place the rules for forwarding parties are specified; other pages refer to it.

### How It Works

The agent signs first, under its own label (`sig1` in the examples on this page), and adds a member under that label to `Signature-Agent`, naming its directory. Every party after it adds its own label (`sig2` for the first hop in the examples), its own `Signature-Agent` member naming **its own** directory, and a signature that is a conformant WG-00 signature in its own right ([The Web Bot Auth Profile](#the-web-bot-auth-profile)). What that signature covers depends on whether the party changed the request. WG-00 §5.2.2 draws the line: a signer MAY cover another signature, and if it covers `"signature";key=X` it MUST also cover `"signature-input";key=X` and every component listed there. A signer that cannot, because it changed a value the inner signature was computed over, MUST NOT cover the inner signature. It signs the request on its own terms, and the inner signature is left untouched.

#### A relay that re-packages the request: FORA's Broker

FORA's Broker re-packages every request it relays. It posts to the Exchange's URL with a new body, so the values the agent's signature covers change, and WG-00 §5.2.2 forbids it to cover the agent's signature. The Broker signs its own request on its own terms:

1. Its signature covers its own request components, `@method`, `@target-uri`, `content-digest` and `authorization`, and exactly one `Signature-Agent` member, its own `"signature-agent";key="<its label>"`.
2. It leaves the agent's `Signature-Agent` member, `Signature-Input` member and `Signature` member untouched, and never covers them. The agent's signature was computed over the request the agent sent, so it does not verify against the re-packaged request, and the Exchange does not rely on it.
3. It appends its own member to `Signature-Agent`, which it can do only when the header is a dictionary. It refuses the legacy single-string form and answers with `Accept-Signature` asking for the dictionary form ([What a FORA verifier accepts](#what-a-fora-verifier-accepts)).

The Exchange authenticates the wire caller as the Broker. Its proof that the agent consented to a transaction does not travel in the transport layer at all: it is the `AgentAcceptance` the agent signed into each item of the body, together with `agent_request_acceptance` for the ordered set ([Projected execute requests](#projected-execute-requests)). Those detached signatures verify against the agent's directory however the request travelled, so they do not depend on the topology. A discovery query moves no money and carries no consent.

Every Broker signature covers exactly one `Signature-Agent` member, so single-member WBA verifiers, such as Cloudflare's `web-bot-auth` library, accept it.

#### A relay that forwards the request unchanged

A party that forwards a request unchanged in every component a previous signature covers MAY cover that signature. If it does, its signature covers its own request components, its own `Signature-Agent` member, and the previous signature: `"signature";key="<previous label>"`, `"signature-input";key="<previous label>"` and every component that signature lists, which includes the previous signer's `Signature-Agent` member. It forwards the earlier `Signature-Agent`, `Signature-Input` and `Signature` members unchanged and appends its own. On such a path the agent signs `@target-uri` against the final recipient's endpoint, not the relay URL it dials.

When every hop covers the signature before it this way, the ordered set of signatures **is** the forwarding chain: it is tamper-evident and order-bound, and no hop can be reordered, removed or inserted without breaking a later signature. This applies only to unchanged forwarding. A re-packaging Broker does not chain; it starts a new request.

### Verification at the Exchange

The Exchange:

1. Reads each labeled signature and its `keyid` from `Signature` / `Signature-Input`
2. Resolves each signature's `keyid` (an RFC 7638 thumbprint) in the key directory that **its own** covered `Signature-Agent` member names, at `{origin}/.well-known/http-message-signatures-directory`. A verifier MUST NOT attribute a signature to a member that signature does not cover (WG-00 §5.2.2)
3. Verifies each signature independently against its own covered components and its own key. It authenticates the caller by the signature of the party that sent the request, the last label added. On unchanged forwarding it also confirms that each hop covers the signature before it, its `Signature-Input` member and every component it lists. A signature left untouched by a re-packaging Broker is not attributed to anyone
4. Enforces depth caps — `RequestConstraints.max_hops` and `WellKnownManifest.max_intermediary_hops` — by **counting the signatures** in the stack

Verifying a hop's signature proves which party sent the request. Whether that party may send to this Exchange at all is the Exchange's own policy: an Exchange MAY accept requests from forwarding parties only when they are Brokers registered with it.

When only the agent's signature is present, the agent is querying the Exchange directly — no broker was involved.

See [Multi-Hop Example (Broker)](#multi-hop-example-broker) below for the concrete header layout.

### Projected execute requests

Projection is one form of the re-packaging described above. When a Broker splits a mixed-Exchange `TransactionRequest` into per-Exchange subrequests, each subrequest has a new body, so the agent's original signature — which covered the original body through `Content-Digest` — cannot travel with it. There is no way to forward a projected body under the agent's HTTP signature, and the protocol does not ask for one.

Instead, each projected subrequest is a **new HTTP request its sender authors**. The projecting party — a Broker, or the agent itself when it splits its own set — computes the subrequest's `Content-Digest` and signs it with its own RFC 9421 signature, exactly as any sender does. The Exchange authenticates the wire caller as that sender.

The agent's cryptographic authorization does not ride the transport layer at all. It rides in the body, as two detached Ed25519 signatures that stay valid however the request travels:

- **`agent_acceptance`** on each item — binds that offer to the requester and the idempotency key.
- **`agent_request_acceptance`** on the request — binds the **complete ordered set** of `(offer signature, exchange)` references, so each Exchange can require its subrequest to be the exact in-order projection of the set the agent signed. See [Broker fan-out and request projection](/components/broker/overview/#execution-separate-step) for the flow.

The Exchange resolves the `agent_request_acceptance` verification key from the requester the signed payload names: the payload's `requester_domain` must equal the request's `requester.domain`, and the signature is accepted only if it verifies against an Ed25519 key currently valid in that domain's WBA directory (`{requester_domain}/.well-known/http-message-signatures-directory`). The envelope carries no `keyid`, so the verifier tries the currently-valid Ed25519 keys of that directory — rotation overlap keeps that set small. When the requester itself signed the arriving request, the request-signing key the Exchange already resolved is that key, and no second fetch is needed. A signature that verifies against a key the requester's domain publishes is what makes the claimed requester identity an authenticated one, the same anchoring every other directory lookup uses.

Delegation is unchanged by projection: the holder-binding check still matches the key that RFC 9421-signed the **arriving** request (see [Which signature binds in a brokered request](#verification)). A projecting Broker is the wire signer, so it may project a delegated request only when the agent has explicitly delegated to the Broker's key — the same terminal-holder rule as narrowing. A pure relay cannot project a delegated request; without a delegation, the Broker simply authenticates as itself while the body's detached signatures carry the agent's authorization.

## Request Signatures (RFC 9421)

### Why headers, not message fields

Request signatures are [RFC 9421 HTTP Message Signatures](https://www.rfc-editor.org/rfc/rfc9421), carried in HTTP headers — **not** fields on any protobuf message. This separates **identity semantics** (the `Requester` message: who is making the request, scopes, delegation) from **cryptographic proof** (the HTTP signature attesting the request is authentic). No FORA message has ever carried a request-signature field; the protobuf body carries identity only, and forwarding is likewise carried in labeled RFC 9421 signatures rather than an in-message hop list (see [Multi-hop forwarding](#multi-hop-forwarding)).

### How RFC 9421 Signatures Work

RFC 9421 defines a standard way to sign HTTP messages. WG-00 profiles it for automated clients. Four headers work together:

| Header | Purpose |
|---|---|
| `Content-Digest` | Hash of the request body (binds the signature to the payload) |
| `Signature-Agent` | Where each signer's key directory is, one dictionary member per signature label |
| `Signature-Input` | Declares which components are signed, the key ID, the algorithm, the validity window and the tag |
| `Signature` | The actual cryptographic signature |

The Exchange verifies the signature by reconstructing the signed content from the declared components, fetching the signer's public key from the key directory the covered `Signature-Agent` member names (selected by the `keyid` thumbprint), and verifying the Ed25519 signature.

### The Web Bot Auth Profile

This section is the normative statement of how FORA request signatures are made and checked. It applies to every FORA request signature: FORA RPCs, forwarded requests, agent requests at the publisher edge, and the retrieval proof of possession a fetcher presents with a signed delivery URL ([Retrieval proof of possession](#retrieval-proof-of-possession)).

#### Every signature: the WG-00 base

Every FORA signature is a conformant WG-00 signature:

| Element | Requirement |
|---|---|
| `Signature-Agent` header | A structured-field **Dictionary** (RFC 9651 §3.2). The member for this signature is `<label>="https://<origin>"`: its key is the signature's label, and its value is the ASCII serialization of an https origin, with no path, query or fragment. Signers use a member key equal to the signature label, and send no `type` parameter, because the default `type`, `directory`, is the one FORA uses |
| `"signature-agent";key="<label>"` | Covered. This binds the signature to the directory it names (WG-00 §5.2.1) |
| `@target-uri` or `@authority` | At least one covered (WG-00 §5.2). FORA RPCs always cover `@target-uri` |
| `created`, `expires` | Both present, as integer seconds. The lifetime is a few minutes and always well under the 24 hours WG-00 recommends as the maximum. A signature is never reused as a long-lived credential (WG-00 §6.9) |
| `keyid` | The key's RFC 7638 JWK thumbprint (RFC 8037 Appendix A.3 for Ed25519), base64url without padding |
| `alg` | `"ed25519"`. WG-00 does not require `alg`, but widely deployed WBA verifiers do, so FORA always sends it |
| `tag` | `"web-bot-auth"` |
| `nonce` | A fresh 64-byte random value for every signature, base64url without padding. See [Replay protection](#replay-protection) |

No other signature parameters are sent.

#### FORA RPCs: the additional components

A FORA RPC carries a body and can move money, so FORA requires more than the WBA base. A signature on a FORA RPC MUST also cover:

| Component | Why |
|---|---|
| `@method` | Narrows the signature to one method |
| `@target-uri` | Narrows the signature to one RPC on one host |
| `content-digest` | WBA covers no body by default (WG-00 §5.2). The RFC 9530 `Content-Digest` header binds the signature to the request body |
| `authorization` | Bound even when empty, so a bearer token cannot be slipped under an existing signature |

This is FORA policy layered on WBA, which WG-00 §5.2.4 permits. It is not a separate signature format. A FORA verifier that refuses a signature for a missing component names the component in the refusal, and answers with an `Accept-Signature` field listing the components it requires (RFC 9421 §5.1, WG-00 §5.3). The covered `"signature-agent";key="sig1"` in it also asks for the dictionary form of `Signature-Agent`:

```http
Accept-Signature: sig1=("@method" "@target-uri" "content-digest" "authorization" "signature-agent";key="sig1");created;expires;tag="web-bot-auth"
```

Any WBA library that can add covered components can therefore call FORA. When the request carries an `X-Entitlement-Token` header, the signature MUST cover that header too.

#### Bodiless requests at the publisher edge

A request at the publisher edge that has no body only identifies an agent and moves no money. The edge accepts the bare WBA base for it: `@authority` or `@target-uri`, the covered `Signature-Agent` member, and the base parameters. It does not require the four FORA components. A request whose signature is missing or does not verify is treated as an unsigned request, not as an identified agent.

#### Retrieval proof of possession

When a delivery URL is bound to the purchasing agent ([Retrieval-URL Identity Binding](#retrieval-url-identity-binding)), the fetch carries a full WBA signature: the WG-00 base above (`tag`, dictionary `Signature-Agent`, the covered `"signature-agent";key="<label>"` member, a 64-byte nonce), plus `@method` and `@target-uri`. The request has no body, so it carries no `content-digest`.

The edge still verifies offline. The fetcher also presents its raw public key in the `X-FORA-Agent-Key` header, and the edge uses that key only when its RFC 7638 thumbprint equals both the signature's `keyid` and the delivery URL's `agent_id`. The binding stays double: the Exchange signed the URL with the thumbprint inside it, and only the holder of the matching private key can produce the request signature. A generic WBA verifier ignores `X-FORA-Agent-Key`, resolves the same key from the agent's directory named in `Signature-Agent`, and accepts the same signature. The edge's full check is on [Signed URL Verification](/components/edge-function/signed-url-verification).

#### What a FORA verifier accepts

Agents in the field run many WBA libraries and some send earlier forms of the protocol. A FORA verifier accepts the following, which WG-00 permits:

- **The legacy `Signature-Agent` form, on a direct single-hop call only.** A bare structured-field String (`Signature-Agent: "https://research.acme.com"`), covered as plain `"signature-agent"`. The verifier treats it as a dictionary with one member whose key is the label of the signature covering it. A relay refuses this form, because it has to append its own member to the agent's `Signature-Agent` header and a String cannot take a second member, and answers with `Accept-Signature` asking for the dictionary form, as in the example below. FORA signers never send this form.
- **A member key different from the signature label.** Signers use a member key equal to the label, but the verifier follows whichever member the signature covers, `"signature-agent";key="<member>"`, whatever the label is called.
- **No `nonce`.** WG-00 sets no nonce requirement.
- **A `type` parameter equal to `directory`** on the member. A member with any other `type` value is ignored, as WG-00 §5.2.1 requires.

A FORA verifier refuses a signature with no `tag` or a `tag` other than `web-bot-auth`, a signature whose covered `Signature-Agent` member is not an https origin, and a bare unquoted `Signature-Agent` value such as `https://research.acme.com`, which is neither a dictionary nor a String. There is no transition window for that last form. A verifier that refuses a signature for a missing component, or for a form it does not accept, answers with `Accept-Signature` naming what it requires (WG-00 §5.3).

A complete WG-00-conformant FORA request. An agent whose directory is `https://research.acme.com` calls `DiscoverResources` on an Exchange directly. "@method": POST

### Replay protection

A verifier that keeps a replay store refuses a signature it has already accepted. The store key is the key ID plus the signature bytes.

Ed25519 signatures are deterministic, and `created` and `expires` are whole seconds. So two identical requests signed in the same second, with no nonce, get the same signature, and the verifier refuses the second one as a replay, although the client sent it on purpose.

To prevent this, every FORA signer adds an RFC 9421 `nonce` parameter to every signature:

- The nonce is 64 random bytes from the platform's cryptographic RNG, encoded as base64url without padding (86 characters). 64 bytes is the length the WBA test vectors use, and widely deployed WBA verifiers refuse a nonce of any other length.
- Each new signing attempt gets a fresh nonce, so a client retry that signs the request again is not refused as a replay. Idempotency keys protect the business operation from running twice.
- Sending the same signed bytes again is still a replay, and the verifier refuses it.
- Verifiers do not require a nonce. A signature without one is still accepted, because WG-00 sets no nonce requirement and other WBA signers omit it.
- The low-level signing helpers (`SignRequest` / `AppendSignature` and their Python and TypeScript equivalents) do not generate a nonce. A caller that uses them directly and needs unique signatures must pass its own fresh nonce.

### No fallback

On FORA RPCs, an RFC 9421 signature that conforms to this profile is the **only** request-authentication mechanism. A request without one (`Signature`, `Signature-Input` and `Signature-Agent`, with a `Content-Digest` over the body) is rejected — there is no proto-field fallback and no degraded mode. There were never any in-message signature fields to fall back to. The publisher edge is different only for bodiless requests, as [Bodiless requests at the publisher edge](#bodiless-requests-at-the-publisher-edge) describes: there a missing or invalid signature means the request is unsigned, and it is never treated as an identified agent.

## Retrieval-URL Identity Binding

A signed `retrieval_endpoint` returned by a transaction is, by default, a bearer token: anyone holding it before `expires_at` can fetch. FORA **optionally** binds the URL to the purchasing agent, DPoP-style ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449)):

- The Exchange embeds `agent_identity_hash` — the [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638) JWK Thumbprint (SHA-256) of the agent's Ed25519 request-signing key — as the URL's `agent_id` query parameter, which the URL signature covers, and echoes it on the execute-path response (`TransactionResponse.agent_identity_hash`, produced directly by the Exchange — the Broker is not in the execute response path for this field).
- A capable delivery endpoint (edge function) verifies the binding without contacting the fetcher's directory: verify the URL's Ed25519 signature against the Exchange's published public key (proves the hash is Exchange-issued and untampered), then require the fetcher to present its public key and a WBA signature over the retrieval request ([Retrieval proof of possession](#retrieval-proof-of-possession)), and check that `thumbprint(presented key)` equals both the signature's `keyid` and `agent_identity_hash`. The fetcher's key arrives in the request, so no directory fetch is needed for it, while a generic WBA verifier can still resolve the same key from the agent's directory. The edge does resolve `kid` to the Exchange's public key, from a cached directory or from keys pinned in its configuration.
- Bound to the request-signing key of whoever fetches, never to the principal/delegation, and exactly one key per transaction. Who that is depends on where the key lives: an agent embedding the SDK holds its own key and fetches for itself, while a custodial agent never fetches at all -- its identity service holds the key and fetches on its behalf. Either way the fetcher is the key holder, which is what the edge checks.
- Enforcement is **NOT mandatory**: a CDN that cannot run code uses its native signed-URL scheme (a CloudFront RSA canned policy, for example) + short TTL + TLS. FORA reference implementations run on edge functions and **do** enforce it.

See [Signed URL Verification](/components/edge-function/signed-url-verification) for the full edge-function verification flow and the stolen-URL threat analysis.


The internal Exchange verifies the delegation JWT against `iam.kirkland.com`'s published key. Because the resource's existence isn't secret here, if the agent requests one outside its scopes the Exchange returns `OFFER_ABSENCE_REASON_SCOPE_INSUFFICIENT` rather than silently omitting it.

### Delegated Sub-Agent (cnf-chained delegation)

The Kirkland legal agent from the previous example delegates to a sub-agent that only needs credit data. It issues a child delegation JWT (bound to the sub-agent's key) that removes legal access and lowers the spend cap.

{/* fora-validate: ResourceQuery */}
```json
{
  "ver": "1.0",
  "exchange": "exchange.example",
  "requester": {
    "id": "credit-checker-sub",
    "domain": "agents.kirkland.com",
    "type": "REQUESTER_TYPE_DELEGATED",
    "name": "Kirkland Credit Sub-Agent",
    "scopes": [
      "credit:read"
    ],
    "delegation": {
      "principal_domain": "iam.kirkland.com",
      "principal_id": "user@kirkland.com",
      "scopes": ["credit:read"],
      "expires_at": "2026-03-20T19:00:00Z",
      "max_spend_cents": 20000,
      "token": "ZXlKaGJHY2lPaUpGWkVSVFFTSjkuPGNoaWxkIGNsYWltczogaXNzLCBzY29wZSwgZXhwLCBjbmYuamt0Pi48c2lnPg",
      "token_format": "jwt"
    }
  },
  "uris": [
    "duns://credit/123456789"
  ],
  "acceptable_restrictions": [
    { "axis": "RESTRICTION_KIND_FUNCTION", "values": ["RETRIEVE"] }
  ]
}
```

Key differences from the parent agent's request:
- `type` is `REQUESTER_TYPE_DELEGATED` — signals this agent acts on behalf of another
- `delegation.scopes` is narrowed to `["credit:read"]` (legal scopes removed)
- `delegation.max_spend_cents` is reduced from `100000` ($1,000) to `20000` ($200)
- `delegation.expires_at` is shortened (1 hour earlier)
- The parent agent's forwarding is recorded **in the HTTP headers**, not the message: the parent adds a labeled RFC 9421 signature, and the sub-agent adds its own signature over the request plus the parent's (see [Multi-hop forwarding](#multi-hop-forwarding))
- The delegation is a JWT chain: the authority JWT (signed by IAM) plus a child JWT (signed by the parent agent) whose `cnf.jkt` binds the grant to the sub-agent's key and whose `scope` is narrowed

The Exchange verifies the full JWT chain: IAM signed the authority JWT; the parent agent signed the child JWT (its signing key matches the authority's `cnf` — chain linkage); the sub-agent's request key matches the child's `cnf.jkt`. No call to IAM was required for the delegation.

## Key Management

### Where Keys Are Published

Every party publishes its keys in **one** place — its WBA directory at `{domain}/.well-known/http-message-signatures-directory`, a pure JWK Set. The role manifest at `{domain}/.well-known/fora.json` (role-tagged) announces *which* party the `{domain}` is; the WBA directory holds its keys. There are no per-role key files; keys are inline JWKs identified by their RFC 7638 thumbprint.

| Party | Key Endpoint (WBA directory) | Role (in `fora.json`) |
|---|---|---|
| Agent / Requester | `{domain}/.well-known/http-message-signatures-directory` | `ROLE_AGENT` |
| Intermediary | `{domain}/.well-known/http-message-signatures-directory` | `ROLE_AGENT` |
| Exchange | `{domain}/.well-known/http-message-signatures-directory` | `ROLE_EXCHANGE` |
| Delegation Issuer (principal / resource owner) | `{domain}/.well-known/http-message-signatures-directory` | `ROLE_AGENT` (key signing delegation JWTs) |

### Key Directory

Every participant serves its keys as a WG-00 key directory (WG-00 §5.5 and §5.5.1):

| Property | Requirement |
|---|---|
| Location | `https://<origin>/.well-known/http-message-signatures-directory`, where `<origin>` is exactly the value of the participant's `Signature-Agent` member |
| Transport | https only |
| Status | `200`, served directly. A verifier does not follow a redirect and treats any other status as a discovery failure |
| Media type | `Content-Type: application/http-message-signatures-directory+json` |
| Body | A JWK Set (RFC 7517 §5): a `keys` array of Ed25519 keys (`kty` `OKP`, `crv` `Ed25519`, `alg` `EdDSA`), plus FORA's optional `revocation_url`. Keys carry no `kid`; a verifier computes each key's RFC 7638 thumbprint and matches it against the signature's `keyid` |
| Signed response | Signed once per listed key, as WG-00 Appendix B.1 describes: the signature covers `"@authority";req` and `content-digest`, carries `created`, `expires`, `keyid` (the thumbprint) and `alg`, and has `tag="http-message-signatures-directory"`. The response carries the matching `Content-Digest` header |
| Access | Reachable without a signature and without bot challenges, and cacheable with standard HTTP caching |

WG-00 makes the signed response RECOMMENDED. FORA requires it, because a directory that is not signed cannot be registered with some widely deployed WBA verifiers. A verifier checks the response signature with the key the directory lists, checks the `Content-Digest` against the body, and refuses a response signature whose `created` is in the future.

FORA adds two extension members to the JWK Set: `not_before` and `not_after` on each key (see [Key Validity Windows](#key-validity-windows)), and `revocation_url` on the set (see [Emergency Revocation](#emergency-revocation)). A generic WBA verifier ignores members it does not know, as RFC 7517 allows.

A complete directory response for the agent in the [Single-Hop Example](#single-hop-example), signed with the same RFC 8037 test key:

```http
Accept: application/http-message-signatures-directory+json
```


`"@authority";req` takes its value from the request that fetched the directory, so the signature cannot be served again under a different host. The `Content-Digest` is computed over the body exactly as shown, with two-space indentation and no trailing newline.

:::note
**Known, deliberate deviation from WG-00 §5.5.1.** A key's `alg` member is `EdDSA`, the JOSE name. RFC 7517 §4.4 defines the JWK `alg` member as a value from the JOSE algorithms registry, and Cloudflare's reference library follows RFC 7517. WG-00 §5.5.1 restricts the same member to HTTP Message Signatures names, where Ed25519 is `ed25519`. FORA follows RFC 7517 and the reference library here. The signature parameter `alg` in `Signature-Input` is a different field and is `ed25519`, as WG-00 requires.
:::

### Key Rotation

Key rotation follows a standard overlap pattern:

1. Publish the new key alongside the old key (both valid)
2. Start signing new requests with the new key
3. After a grace period (Exchange-defined, typically 24-48 hours), remove the old key
4. Exchanges SHOULD cache keys with a TTL and re-fetch periodically

For delegation JWTs, key rotation at the issuer does not invalidate existing tokens — the authority JWT was signed with the key that was current at issuance time. Exchanges SHOULD accept tokens signed by recently-rotated keys within a configurable grace period.

### Key Validity Windows

Each `JsonWebKey` carries RFC3339 `not_before` / `not_after` bounds. The window is **half-open** `[not_before, not_after)` — a key is valid at `not_before` and invalid **at and after** `not_after`. At least one key in the WBA directory's `keys` MUST be valid at serve time, and verifiers MUST reject signatures whose key falls outside its window.

### Caching Contract

The WBA directory (`/.well-known/http-message-signatures-directory`) and `/.well-known/fora.json` MAY be cached by consumers and CDNs for routine periods (minutes to hours) — keys rotate slowly and carry explicit bounds. The `revocation_url` body, by contrast, SHOULD be served with a short or zero freshness lifetime (e.g. `Cache-Control: max-age=60`, or `no-store`) so the 300s revocation poll is not defeated by an intermediary cache.

Enforcement is operational, not protocol-guaranteed: a consumer that grants access against a stale revocation set bears that as its own business risk — it is not a protocol deficiency.

### Emergency Revocation

When a WBA directory sets `revocation_url`, consumers poll it on a 300s cadence (±10% jitter) and replace their local revoked set with the response — a `KeyRevocationList` (thumbprint-only snapshot: `as_of` + `revoked[]`). A revoked thumbprint stays revoked; reject any signature whose key thumbprint is in the set. When `revocation_url` is unset, consumers rely on routine rotation and `not_after` expiry.

### Domainless Agents

An individual agent with no public domain of its own is accommodated **without a protocol change**: a registry (operated by an Exchange/Broker or a third party) hosts the agent's `WellKnownManifest`, and the agent sets `Requester.domain` to that registry host (e.g. `agent-7.registry.example`). The agent generates its own keypair; the registry publishes the public half in its WBA directory at `{registry}/.well-known/http-message-signatures-directory`. The domain + well-known paradigm is preserved end to end. Relaxing the discovery anchor (an explicit per-requester keys URL) is a deliberate deferral.
