## Overview

FORA-Music v1 defines a standardized vocabulary of `ext` field keys for music recordings traded through FORA Exchanges. It enables agents and Brokers to:

- **Discover** recordings by genre, sub-genre, theme, mood, instruments, suitability, energy, vocals, tempo, duration, release date, language, parental warning and AI content
- **Filter** a catalog search with required `music.*` constraints in `DiscoveryRequest.search_filters`
- **Find** a specific recording by its ISRC, a release by its UPC or GRid, and every recording of one work by its ISWC
- **Show** the release and credit block that a label keeps for every recording: title, release title and date, label, catalog number, P-line and C-line, contributors and artwork

The profile is recording-discovery metadata. It is not a rights model: it has no fields for composition ownership, royalty splits or clearance. Permission to use a recording comes only from the offer's [license terms](/protocol/licensing-terms/).

### Who Should Implement This

- **Exchanges** serving music libraries, production music catalogs or labels
- **Brokers** that search music catalogs by musical facets
- **Agents** that choose music for videos, podcasts, games or other productions

### Prerequisites

Implementers must be familiar with:

- FORA protocol (`proto/fora/v1/fora.proto`)
- The `ext` field mechanism (`google.protobuf.Struct` on all major messages)
- The `Offer` and `DiscoveryRequest` messages

[Live Demo: Music](/getting-started/live-demo-music/) shows the profile in use: an agent finds a track and buys a license to use it in a video.

## Profile Declaration

An Exchange declares support for this profile by including `"fora-music-v1"` in its `WellKnownManifest.supported_profiles` array (`role=ROLE_EXCHANGE`):

```json
{
  "ver": "1.0",
  "role": "ROLE_EXCHANGE",
  "domain": "music-exchange.example.com",
  "name": "Example Music Exchange",
  "supported_profiles": ["fora-music-v1"],
  "endpoint": "https://music-exchange.example.com/fora/v1"
}
```

For this profile, the declaration means one thing: the Exchange forwards the publisher's `music.*` keys unchanged inside the signed offer. The Exchange does not validate them. It treats `fora-news-v1` the same way. This is narrower than the general rule in [Extension Profiles](/protocol/extension-profiles/), which says that an Exchange validates profile fields against the profile's JSON Schema.

The Broker does not route requests by `supported_profiles`.

## Offer Metadata (`Offer.ext`)

Each field is one key of `Offer.ext`, named `music.<field>`, like the keys of the news, academic and legal profiles (for example `news.section`). In a [catalog feed](/protocol/jsonl-ingestion/) record the keys are in the record's `ext`, and the Exchange copies the record's `ext` into `Offer.ext` before it signs the offer.

An offer carries fora-music-v1 metadata when its `ext` has at least one `music.<field>` key. A nested `ext.music` object is not part of the profile: consumers treat the key `music` as an unknown key.

The search filter keys use the same names: `music.genre` filters on the field whose key is `music.genre`. This page names a field without its prefix (`genre`, `vocals`) when the meaning is clear.

| Key | Type | Required | Used for Matching | Description |
|-----|------|----------|-------------------|-------------|
| `music.artist` | string | Optional | No | Display credit. Case is preserved. It does not identify the publisher, the rights owner or a contributor. |
| `music.title` | string | Optional | No | Display title of the recording. Case is preserved. |
| `music.isrc` | string | Optional | Yes | ISRC of the **source recording**: 12 characters without hyphens (`^[A-Z]{2}[A-Z0-9]{3}[0-9]{7}$`). When the delivered file is an excerpt or an edit, `isrc` still names the source recording. |
| `music.genre` | label | Optional | Yes | One primary genre. |
| `music.subgenres` | label[] | Optional | Yes | Finer genre labels under the primary genre, for example `lo-fi` or `bebop`. |
| `music.themes` | label[] | Optional | Yes | What the music or the lyrics are about, for example `christmas`, `summer` or `travel`. |
| `music.mood` | label[] | Optional | Yes | Moods. |
| `music.instruments` | label[] | Optional | Yes | Instruments heard in the file. Category labels such as `brass` or `strings` are valid. |
| `music.suitable_for` | label[] | Optional | Yes | Editorial suitability, for example `vlog`, `documentary` or `trailer`. It does not give permission to use the file. |
| `music.energy` | string | Optional | Yes | Editorial energy level: `low`, `medium` or `high`. It does not depend on `bpm`. |
| `music.vocals` | boolean | Optional | Yes | See [Vocals](#vocals). |
| `music.bpm` | integer | Optional | Yes | Tempo in beats per minute, 1 or more. Fractional BPM is not supported. |
| `music.duration_seconds` | number | Optional | Yes | Duration of the **delivered file**, more than 0. For a 60-second excerpt it is the excerpt's duration (for example `60.03`), not the duration of the source recording. |
| `music.version` | label | Optional | No | Which version of the recording this is, for example `instrumental`, `live`, `remix` or `radio`. |
| `music.language` | string | Optional | Yes | Language of the performance as a BCP 47 tag, for example `en` or `pt-BR`. See [Language](#language). |
| `music.parental_warning` | string | Optional | Yes | `explicit`, `explicit_edited` or `not_explicit`. See [Parental Warning](#parental-warning). |
| `music.contains_ai` | boolean | Optional | Yes | `true` when the recording contains AI-generated content. See [AI Content](#ai-content). |

`artist`, `title` and `version` are descriptive. No search filter refers to them. `isrc` is used only by the `music.isrc` filter, as an exact match.

### Release, Identifiers and Credits

These fields describe the release the recording belongs to, and the credits a label keeps for it. The identifier formats are in [Identifiers](#identifiers), and the contributor object is in [Contributors](#contributors).

| Key | Type | Required | Used for Matching | Description |
|-----|------|----------|-------------------|-------------|
| `music.release_title` | string | Optional | No | Display title of the album, EP or single the recording was released on. |
| `music.release_date` | string | Optional | Yes | Date the release was first made available: `YYYY`, `YYYY-MM` or `YYYY-MM-DD`. See [Release Date](#release-date). |
| `music.label` | string | Optional | Yes | Name of the record label of the release. Case is preserved. |
| `music.catalog_number` | string | Optional | No | The label's own number for the release. It is meaningful only together with `label`. |
| `music.upc` | string | Optional | Yes | UPC or EAN of the release: 12 to 14 digits. |
| `music.grid` | string | Optional | Yes | Global Release Identifier of the release: 18 characters. |
| `music.iswc` | string | Optional | Yes | ISWC of the **work** (the composition), in the compact form `T` and 10 digits. |
| `music.proprietary_ids` | string[] | Optional | No | The publisher's own identifiers of the recording, each as `namespace:value`, for example `fma:12345`. |
| `music.p_line` | string | Optional | No | The full P-line (phonogram notice), for example `(P) 2015 Example Records`. |
| `music.c_line` | string | Optional | No | The full C-line (copyright notice), for example `(C) 2015 Example Music Publishing`. |
| `music.contributors` | object[] | Optional | No | Credits: who did what. Each object has `name`, `role`, and optional `instrument` and `isni`. |
| `music.artwork_url` | string | Optional | No | URL of the cover image. |

`upc`, `grid` and `iswc` are matched like `isrc`: each only by the filter of the same name, as an exact match.

### Labels

`genre`, `subgenres`, `themes`, `mood`, `instruments`, `suitable_for` and `version` hold labels, and so do the `role` and `instrument` of a contributor. A label:

- is not empty;
- has no whitespace at the start or at the end;
- has no upper-case or title-case letter.

Both rules use Unicode. Whitespace includes the non-breaking space. Upper case and title case are the Unicode categories Lu and Lt, so `électronique` is a label and `Électronique` is not.

Consumers do no stemming and no singular/plural matching, so `guitar` and `guitars` are different labels. The feed must use one label for one thing.

A publisher that fills a label from a DDEX allowed value writes the value as a label: split the CamelCase value into words, lower-case them, and join them with one space. `HipHop` becomes `hip hop`, `FeelingGood` becomes `feeling good`, `4OnTheFloor` becomes `4 on the floor`, and `R'n'B` becomes `r'n'b`. [Recommended Labels](#recommended-labels) lists the result for the DDEX value sets this profile uses, so that two publishers spell the same thing the same way.

`language` is not a label. It is a BCP 47 tag, and consumers compare it case-insensitively.

### Vocals

`vocals` describes the delivered file. It is `true` when the file contains any human voice that can be heard: sung lyrics, wordless singing, choir or spoken word. It is `false` only when the file contains no human voice.

The definition is broad on purpose. An agent that filters on `vocals: false` usually needs a track that does not compete with narration, and any voice does.

### Release Date

`release_date` is the date the release was first made available, in the form `YYYY`, `YYYY-MM` or `YYYY-MM-DD`. A publisher writes the parts it knows: `2015` when only the year is known. It is not the date the file was uploaded, and not the date the offer was made.

### Identifiers

- `upc` is the UPC or EAN of the release: 12 to 14 digits. The last digit is the GS1 check digit. The publisher checks it before it sends the feed. The schema checks only the digit count, because a JSON Schema pattern cannot compute a check digit.
- `grid` is the Global Release Identifier of the release: 18 characters without hyphens. They are `A1`, a 5-character issuer code, a 10-character release number and a check character.
- `iswc` identifies the work (the composition), not the recording. It is written in the compact form: `T` followed by 10 digits, for example `T0345246801`. The display form `T-034.524.680-1` is written without its hyphens and dots, the same way `isrc` is written without hyphens.
- `isni` on a contributor identifies the person or group: 16 characters without spaces, 15 digits and a check character `0` to `9` or `X`.
- `proprietary_ids` holds the publisher's own identifiers of the recording. Each entry is `namespace:value`, for example `fma:12345`. The namespace is a DNS name or a short name of the source.

`isrc`, `upc`, `grid` and `iswc` name the recording, the release and the work that a license covers, so a usage report or a dispute can name them. They say nothing about who owns the work.

### Contributors

`contributors` is an array of objects, one per credit. Each object has these keys:

| Key | Type | Required | Description |
|-----|------|----------|-------------|
| `name` | string | Yes | Display name of the person or group. Case is preserved. |
| `role` | label | Yes | What the contributor did, for example `composer`, `lyricist` or `mixing engineer`. [Recommended Labels](#recommended-labels) lists the roles. |
| `instrument` | label | Optional | The instrument the contributor played, for a performer. |
| `isni` | string | Optional | ISNI of the person or group. See [Identifiers](#identifiers). |

A person with two roles appears twice, once per role. An empty array means known to be empty, like every array of this profile. An absent key means the credits are unknown.

### Language

`language` is the language of the sung or spoken words as a BCP 47 tag, for example `en`, `de` or `pt-BR`. It is not a label: upper-case letters are allowed, and consumers compare it case-insensitively. An instrumental recording leaves it out.

### Parental Warning

`parental_warning` is `explicit`, `explicit_edited` or `not_explicit`. `explicit_edited` means an edited version of an explicit recording. When the publisher has no advice, it leaves the key out.

### AI Content

`contains_ai` is `true` when the recording contains AI-generated content, and `false` when the publisher states that it contains none. An absent key means unknown. It never means `false`.

### Absent, Empty and Null

- An absent field means "unknown". An absent `vocals` never means `false`.
- An empty array means "known to be empty". It is different from an absent array.
- `null` is not a valid value, and the schema rejects it. A publisher leaves out an unknown field. A consumer that receives `null` treats the field as absent.
- Consumers ignore fields they do not know. A publisher can send other fields, for example an identifier this profile does not define, and consumers still work. A field is added to this profile when a consumer uses it.

## Query Vocabulary (`DiscoveryRequest.search_filters`)

An agent can limit a catalog search with `DiscoveryRequest.search_filters`. The Broker answers these filters only when its catalog search (query discovery) is switched on.

| Key | Type | Required | Description |
|-----|------|----------|-------------|
| `music.isrc` | string or string[] | Optional | ISRC, 12 upper-case characters without hyphens (`^[A-Z]{2}[A-Z0-9]{3}[0-9]{7}$`). The match is exact. An array must not be empty. Example: `"USXXX2300011"`. |
| `music.genre` | label or label[] | Optional | Genre. An array must not be empty. Example: `"cinematic"`, `["jazz", "blues"]`. |
| `music.mood` | label or label[] | Optional | Mood. An array must not be empty. Example: `"calm"`. |
| `music.instruments` | label or label[] | Optional | Instruments. An array must not be empty. Example: `["piano", "strings"]`. |
| `music.suitable_for` | label or label[] | Optional | Editorial suitability. An array must not be empty. Example: `"trailer"`. |
| `music.energy` | string or string[] | Optional | `low`, `medium` or `high`. An array must not be empty. Example: `"high"`. |
| `music.vocals` | boolean | Optional | Example: `false`. |
| `music.bpm_range` | string | Optional | `MIN-MAX`, `MIN-` or `-MAX` with positive integers. Both bounds are inclusive, and `MIN` is not greater than `MAX`. Example: `"115-125"`, `"120-"`. |
| `music.duration_seconds_range` | string | Optional | `MIN-MAX`, `MIN-` or `-MAX` with positive numbers of seconds. Both bounds are inclusive, and `MIN` is not greater than `MAX`. Example: `"30-90"`, `"-60.5"`. |
| `music.upc` | string or string[] | Optional | UPC or EAN, 12 to 14 digits. The match is exact. An array must not be empty. Example: `"020123456782"`. |
| `music.grid` | string or string[] | Optional | GRid, 18 characters without hyphens. The match is exact. An array must not be empty. Example: `"A10302B0001234567D"`. |
| `music.iswc` | string or string[] | Optional | ISWC in the compact form, `T` and 10 digits. The match is exact. An array must not be empty. Example: `"T0345246801"`. |
| `music.label` | string or string[] | Optional | Record label name. The match is case-insensitive and otherwise exact. An array must not be empty. Example: `"Example Records"`. |
| `music.release_date_range` | string | Optional | `START/END`, `START/` or `/END` with dates in the `YYYY`, `YYYY-MM` or `YYYY-MM-DD` form. Both bounds are inclusive, and `START` is not after `END`. The separator is `/` (the ISO 8601 interval form), because `-` is part of a date. Example: `"2015/2019"`, `"2020-06/"`, `"/1999-12-31"`. |
| `music.parental_warning` | string or string[] | Optional | `explicit`, `explicit_edited` or `not_explicit`. An array must not be empty. Example: `"not_explicit"`. |
| `music.language` | string or string[] | Optional | BCP 47 tag. The match is case-insensitive, and a tag also matches the longer tags that start with it: `pt` matches `pt-BR`. An array must not be empty. Example: `"es"`. |
| `music.subgenres` | label or label[] | Optional | Sub-genres. An array must not be empty. Example: `["lo-fi", "ambient"]`. |
| `music.themes` | label or label[] | Optional | Themes. An array must not be empty. Example: `"christmas"`. |
| `music.contains_ai` | boolean | Optional | Example: `false`. |

A range key is the name of the field it limits, followed by `_range`. A value outside its format, for example `music.release_date_range: "2015-2019"` or `music.upc: "ABC"`, rejects the whole request with `INVALID_ARGUMENT`; see [Order of Checks and Errors](#order-of-checks-and-errors). A key this profile does not define is ignored.

### How Filters Match

- Filters are required. A track must match every filter key. When a key has several values, the track must match at least one of them. In other words, the values of one key are combined with OR, and the keys are combined with AND.
- A track with an unknown field does not match a filter on that field.
- `music.isrc` matches a track only when the track's `music.isrc` is exactly one of the given values. The Broker never reads an ISRC from the free-text `query`, so only this filter finds a track by its ISRC. `music.upc`, `music.grid`, `music.iswc` and `music.parental_warning` match the same way.
- `music.label` and `music.language` match case-insensitively. For `music.language`, a given tag also matches a longer tag with the same prefix: `pt` matches `pt` and `pt-BR`, and `pt-BR` matches only `pt-BR`.
- `music.subgenres` and `music.themes` match like `music.mood`: the track has at least one of the given labels.
- `music.release_date_range`: a bound with fewer parts covers its whole period, so `2015` as `START` means 2015-01-01 and as `END` means 2015-12-31. A track's `release_date` is read the same way, and the track matches when its whole period is inside the range. A track dated `2015` matches `2010/2019` and does not match `2015-06/`, because its month is unknown.
- `music.contains_ai` works like `music.vocals`: a track without the key does not match `false`.
- The Broker also reads tags from the free-text `query`. These tags are preferences, and they apply only to the tracks that pass every filter. Among those tracks, the tracks that match the most query tags come first. When no passing track matches a query tag, or the query has no known tag, the Broker returns every track that passes the filters. A query tag never adds a track that fails a filter.
- When both the filters and the query give bounds for the same field, the Broker uses the overlap of the two ranges. If the ranges do not overlap, no track matches.
- A request with filters and no `query` does not call the query model. This includes a request with only an identifier filter such as `music.isrc`, or only a range filter such as `music.bpm_range`.
- A valid filter value that no track has, for example `music.genre: "funk"` in a catalog without funk, matches no track. The answer is `NOT_IN_CATALOG`. The Broker never drops such a filter.

### Order of Checks and Errors

The Broker checks a request in this order:

1. **Explicit URIs come first.** When the request lists `uris`, the Broker resolves them and ignores `query` and `search_filters`. It does not validate the filters, and the query discovery switch does not apply.
2. **Unknown keys are ignored.** A key that this profile does not define is ignored, for example `music.tempo` or a key of another profile.
3. **Invalid values are rejected.** A defined key with a value outside its format rejects the request with `INVALID_ARGUMENT`, and no search runs. Examples: `music.bpm_range: "fast"`, an upper-case label, an ISRC with hyphens or lower-case letters, a UPC with a letter, a `music.release_date_range` written with a dash (`2015-2019`) or with the month `13`, a `music.parental_warning` outside its three values, an empty array.
4. **A search input is required.** A request with no `uris`, no `query` and no defined filter key is rejected with `INVALID_ARGUMENT`. This is the same as a request with neither `query` nor `uris`.
5. **Filters need catalog search.** When the Broker's query discovery is switched off, a request with a defined filter key is rejected with `UNIMPLEMENTED`. The Broker in this configuration cannot apply the filters, and it must not return results that ignore them. The code is not `INVALID_ARGUMENT`, because the request is valid. It is not `FAILED_PRECONDITION`, because the caller cannot change the Broker's configuration.

### Older Brokers

Check 2 also covers a filter key that this profile defined after the Broker was built. Such a Broker ignores the key: the request succeeds, and the results are not filtered by that key. The response does not tell the agent which filter keys the Broker applied. This is accepted, because the Broker version is known in a deployment. New offer keys need no such rule: a consumer ignores the keys it does not know, and the offer stays valid.

## Behavioral Conventions

### Validation

| Party | What it checks |
|---|---|
| The [JSON Schema](#json-schema) | The shape of every field: the identifier formats, the date form, the three parental-warning values, the contributor objects and the label format. It does not check the UPC check digit. |
| Broker | The 19 matching fields, when it loads its catalog feed. An invalid matching field fails the load, and the error names the record and the field. The Broker does not read the descriptive fields. |
| Exchange | Nothing. It forwards the `music.*` keys unchanged inside the signed offer, so the offer signature covers every key, including unknown ones. |

### Tempo Groups

Tempo groups such as slow, medium and fast are Broker behavior. They are not part of the profile. The profile carries only the exact `bpm`.

### Example 1: Music Track Offer

An Exchange returns an offer for a 60-second excerpt of an instrumental track, with the release and credit block the label keeps for it. The offer sells a one-time license for one personal video. The `terms` are shortened; see [Licensing Terms](/protocol/licensing-terms/).

```jsonc

  "title": "Galaxy Drift — Nova Orbit",
  "pricing": {
    "model": "PRICING_MODEL_FLAT",
    "rate": "29",
    "currency": "EUR",
    "metering": "PRICING_METERING_NONE"
  },
  "delivery_method": "DELIVERY_METHOD_DIRECT",
  "identity": {
    "canonical_url": "https://music-exchange.example.com/tracks/galaxy-drift-loop.mp3",
    "content_hash": "sha256:b430ef4d...",
    "hash_method": "sha256",
    "resource_mutability": "RESOURCE_MUTABILITY_STATIC"
  },
  "terms": [ /* one LicenseTerm: individuals, one personal video */ ],
  "ext": {
    "music.artist": "Nova Orbit",
    "music.title": "Galaxy Drift",
    "music.genre": "electronica",
    "music.subgenres": ["downtempo", "ambient"],
    "music.themes": ["space"],
    "music.mood": ["grooving", "mysterious"],

    "music.release_title": "Galaxy Drift",
    "music.release_date": "2015-06-17",
    "music.label": "Example Records",
    "music.catalog_number": "EXR-0042",
    "music.upc": "020123456782",
```

### Example 2: Filtered Discovery Request

An agent asks for funk tracks between 115 and 125 BPM with no vocals, released in 2015 or later and without an explicit-content warning, for a cooking video:

```json
{
  "query": "upbeat background music for a cooking video",
  "search_filters": {
    "music.genre": "funk",
    "music.bpm_range": "115-125",
    "music.vocals": false,
    "music.release_date_range": "2015/",
    "music.parental_warning": "not_explicit"
  }
}
```

The Broker returns only tracks with `music.genre: "funk"`, a `music.bpm` from 115 to 125, `music.vocals: false`, a `music.release_date` in 2015 or later and `music.parental_warning: "not_explicit"`. A track with no `music.vocals` key, no `music.release_date` key or no `music.parental_warning` key is not returned. Among the tracks that pass, the tracks that match the most tags the Broker reads from the `query` come first. If the catalog has no funk track, the answer is `NOT_IN_CATALOG`.

### Example 3: Rejected Filter

An agent sends a tempo word instead of a range:

```json
{
  "query": "fast drum and bass",
  "search_filters": {
    "music.bpm_range": "fast"
  }
}
```

`"fast"` is not in the `MIN-MAX`, `MIN-` or `-MAX` format, so the Broker rejects the request with `INVALID_ARGUMENT` and runs no search. The agent can send `"music.bpm_range": "160-"`, or leave the tempo in the free-text `query`. A date range written with a dash, `"music.release_date_range": "2015-2019"`, is rejected the same way: the separator of a date range is `/`.

## Conformance

The profile defines no conformance levels. Every field is optional, and a publisher sends the fields it knows.

- An **Exchange** that declares `fora-music-v1` MUST forward the publisher's `music.*` keys unchanged inside the signed offer. It does not validate them.
- A **Broker** that answers `music.*` search filters MUST apply them as required constraints, in the [order of checks](#order-of-checks-and-errors) above. When its catalog search is switched off, it MUST reject a request with a defined filter key with `UNIMPLEMENTED`.
- A **publisher** can validate the `ext` of each record against the [JSON Schema](#json-schema) before it pushes the feed. This finds the errors early, because the Broker refuses a feed with an invalid matching field.

## SDK Types

The SDKs have a typed view of the `music.*` keys of `Offer.ext`:

| Language | Import | Names |
|---|---|---|
| Go | `github.com/FORA-Protocol/protocol/sdk/go/profiles/music` | `music.Music`, `music.Contributor`, `music.ProfileID` |
| TypeScript | `@fora-protocol/sdk/music` | `Music`, `Contributor`, `ProfileID` |
| Python | `fora_sdk.music` | `Music`, `Contributor`, `PROFILE_ID` |

`Contributor` is the type of one entry of `music.contributors`, with `name`, `role` and the optional `instrument` and `isni`. The types keep the rules from [Absent, Empty and Null](#absent-empty-and-null): an absent key stays absent, and an empty list stays an empty list. Decoding an `Offer.ext` into the Go type keeps only the `music.*` keys. A `music.bpm` written as a whole number with a fraction or an exponent, for example `90.0` or `1e2`, is valid, because JSON Schema counts it as an integer. The Go type accepts it as `90` or `100`. The types do not validate the values. Use the JSON Schema to validate input that you do not trust.

The schema is `music-v1.schema.json` (JSON Schema Draft 2020-12). It applies to the whole `ext` object and allows other keys, including unknown `music.*` keys.

### Validating in Python

The label pattern uses Unicode property classes (`\p{Z}`, `\p{Lu}`, `\p{Lt}`). JSON Schema allows them, because it uses ECMA-262 regular expressions. Python's `re` module does not support them. The standard `pattern` check of the Python `jsonschema` package uses `re`, so `jsonschema.validate()` fails on any object that has a label field, with the error `bad escape \p`.

Validators in Go and JavaScript that follow ECMA-262, such as `santhosh-tekuri/jsonschema` and Ajv 8, need no change.

In Python, replace the `pattern` check with one that uses the `regex` package, which supports these classes. Install both packages:

```sh
pip install jsonschema regex
```

Then build the validator from the extended class, and use it for every check. Do not call `jsonschema.validate()` directly, because it uses the standard `pattern` check.

```python
import json

import regex
from jsonschema import Draft202012Validator, ValidationError, validators


def _unicode_pattern(validator, pattern, instance, schema):
    # Replaces the standard "pattern" check, which uses Python's re module.
    # The regex module supports the \p{...} classes that the label pattern uses.
    if validator.is_type(instance, "string") and not regex.search(pattern, instance):
        yield ValidationError(f"{instance!r} does not match {pattern!r}")


MusicValidator = validators.extend(Draft202012Validator, {"pattern": _unicode_pattern})

with open("music-v1.schema.json", encoding="utf-8") as f:
    validator = MusicValidator(json.load(f))

music = {"music.genre": "Jazz", "music.bpm": 90}
for error in validator.iter_errors(music):
    print(f"{error.json_path}: {error.message}")
```

This prints the error for the upper-case label `Jazz`. Save the schema above as `music-v1.schema.json` before you run it.

## Out of Scope

- Rights-model fields: composition ownership, royalty splits, clearance.
- Identifiers other than ISRC, ISWC, UPC, GRid and the contributor's ISNI: IPI, DPID, ISAN, EIDR, HFA. Publishers can send them as unknown fields.
- Rights data from DDEX deal terms (territory, use type, commercial model, validity period). It maps to the offer's [license terms](/protocol/licensing-terms/), not to this profile.
- Broker routing by `supported_profiles`.
- Validation of the `music.*` keys by the Exchange.

## Recommended Labels

This section is not normative. Labels stay free. The lists below are the DDEX allowed values this profile's fields correspond to, written with the normalization rule from [Labels](#labels), so that two publishers spell the same thing the same way. The Broker matches labels exactly, so a shared spelling is what makes a filter find a track. The DDEX value `UserDefined` and the values DDEX has deprecated are left out.

**`music.genre`**, from avs:ClassifiedGenre: `blues`, `classical music`, `country music`, `electronic music`, `folk`, `gospel`, `hip hop`, `jazz`, `latin`, `pop`, `r'n'b`, `reggae`, `rock`, `spoken`, `traditional`, `world music`.

**`music.instruments`** and a contributor's **`instrument`**, from avs:InstrumentType. The set has about 750 values arranged in families. A publisher uses the most specific value it knows, and the family name when it knows only the family:

- `string instrument`: `banjo`, `bass`, `bass guitar`, `cello`, `double bass`, `fiddle`, `guitar`, `acoustic guitar`, `electric guitar`, `harp`, `lute`, `mandolin`, `ukulele`, `viola`, `violin`, `zither`

- `synthesizer`, `drum machine`, `sampler`, `turntable`
- `voice`, `choir`

**`music.version`**, from avs:VersionType, with the word `Version` dropped before normalization: `a cappella`, `album`, `alternative`, `demo`, `instrumental`, `karaoke`, `live`, `mix`, `mono`, `radio`, `remix`, `session`, `single`, `stereo`.
