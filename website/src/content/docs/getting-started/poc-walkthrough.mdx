You can run the whole protocol today, from a chat window, in about five minutes. No signup fee, no contract, no card. This page walks the demo as a user sees it, and shows the protocol call sitting under each screen.

The short version: there is a demo publisher whose content **refuses AI agents at the door**. You will watch an agent get turned away, then watch the same agent buy a licence and read the same bytes — signed, priced, and reported.

<Aside type="caution" title="It is a demonstration, not a service">
Licensed content is fictional sample data with no real rights attached. Balances are test money, so nothing is billed or owed. The deployment can be reset without notice, which removes accounts, registrations and transaction history.
</Aside>

## What you need

Claude with custom connector support, and an email address you can receive mail at. That is all.

## 1. Add the demo MCP server

Add a custom connector pointing at the demo MCP endpoint:

```
https://mcp.demo.fora-protocol.org/mcp
```

<Image src={addConnector} alt="Claude's Add custom connector dialog, with the name FORA and the demo MCP URL filled in." />

Claude probes the endpoint and discovers how to authenticate. Both settings it picks are the right ones — the server runs an OAuth flow, and registers OAuth clients dynamically as users connect.

<Image src={connectorAuth} alt="Connector settings showing Sign in now and Register automatically, both marked Detected." />

<Aside title="What was discovered">
The endpoint answers an unauthenticated request with `401` and the OAuth metadata that tells a client where to send the user. Confirm it yourself:

```bash
curl -si https://mcp.demo.fora-protocol.org/mcp | head -1
# HTTP/2 401
```
</Aside>

### What actually happened

Registering did not just create a login. The demo provisioned you a full protocol participant:

1. **A subdomain of your own** — `agent-<id>.mcp.demo.fora-protocol.org`.
2. **An Ed25519 keypair**, generated and held server-side.
3. **A published key directory** at that subdomain, so any verifier can resolve your public key.

That directory is live and world-readable. This is the identity from the screenshot above, still serving:

```bash
curl -s https://agent-duci2vuk.mcp.demo.fora-protocol.org/.well-known/http-message-signatures-directory
```

```json
{
  "keys": [{
    "kty": "OKP", "crv": "Ed25519", "use": "sig", "alg": "EdDSA",
    "x": "EdbIZlG3BxFrQOyALo83-2atoIFh5zhzbT1c9L6asa4",
    "not_before": "2026-09-17T07:38:33Z",
    "not_after": "2027-09-17T07:38:33Z"
  }],
  "revocation_url": "https://agent-duci2vuk.mcp.demo.fora-protocol.org/.well-known/fora-key-revocations.json"
}
```

From here on, every protocol call made on your behalf is signed with that key ([RFC 9421](https://www.rfc-editor.org/rfc/rfc9421) HTTP Message Signatures), carries that hostname in a covered `Signature-Agent` header, and is verified by the Exchange against exactly the directory above. The `keyid` is the key's [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638) thumbprint.

<Aside type="tip" title="MCP is the convenience layer, not the protocol">
Nothing above is specific to MCP or to Claude. The MCP server holds a key and signs on your behalf because that is convenient inside a chat client. An agent that holds its own key, publishes its own directory and signs its own requests is the same participant to the Exchange, and speaks the same wire. See [Authentication](/protocol/authentication/) for the signing rules and [For AI Agents](/getting-started/for-ai-agents/) for the client-side path.
</Aside>

## 4. Register with the Exchange

Ask Claude to register you. It reads the Exchange's manifest, finds what the Exchange asks for, reads the terms, and registers.

<Image src={exchangeRegister} alt="Claude reading the registration schema, accepting terms, and reporting a successful registration with exchange, legal entity, email, billing ref and active status." />

The Exchange publishes what it wants in its manifest, which is why the agent can do this unattended:

```bash
curl -s https://exchange.demo.fora-protocol.org/.well-known/fora.json
```

```json
{
  "ver": "1.0",
  "role": "ROLE_EXCHANGE",
  "domain": "exchange.demo.fora-protocol.org",
  "endpoint": "https://exchange.demo.fora-protocol.org",
  "terms_uri": "https://exchange.demo.fora-protocol.org/terms/revision-1.txt",
  "supported_profiles": ["fora-news-v1", "fora-comp-v1"],
  "base_currency": "EUR",
  "max_intermediary_hops": 4,
  "account_registration": {
    "data_schema": {
      "type": "object",
      "required": ["legal_entity"],
      "properties": {
        "legal_entity": { "type": "string", "minLength": 1, "maxLength": 200 },
        "email":        { "type": "string", "maxLength": 254 }
      }
    }
  },
  "terms_digest": "sha256:d51eaaff39d8f2497efd20e34709bddbffad99761deff14de216806a32460785"
}
```

`legal_entity` required, `email` optional — exactly what the agent reported back. The `terms_digest` it echoed is the one above: registration records **which revision of the terms you accepted**, by digest, so neither side can later disagree about what was agreed.

## 5. Watch the door close

Now the point of all this. Ask Claude to fetch an article from the demo publisher directly.

<Image src={directFetch} alt="Claude reporting that it could not fetch the page because the site blocked its request as automated traffic." />

It is refused. The publisher serves that content happily to a browser and refuses it to an AI agent, which is a real posture a growing number of publishers have adopted.

You can reproduce the asymmetry in two commands:

```bash
URL=https://demo.fora-protocol.org/articles/philosophers/md/leucippus.md

curl -s -o /dev/null -w '%{http_code}\n' -A 'Mozilla/5.0' "$URL"
# 200

curl -s -o /dev/null -w '%{http_code}\n' -A 'ClaudeBot/1.0 (+claudebot@anthropic.com)' "$URL"
# 403
```

<Aside title="What is being refused, precisely">
Not you — your *agent*. The block is on the agent user-agent, not on the network or the content. FORA's claim is not that content is unreachable; it is that an agent has no way to *transact* for it. That is the gap the next step closes.
</Aside>

## 6. Buy the licence instead

Ask for the same URL again, and let the agent use the protocol.

<Image src={foraFetch} alt="Claude discovering the offer, executing the transaction, reporting usage, and then displaying the full licensed article." />

Four calls, and the article arrives:

1. **`Fora discover`** — the Exchange returns an offer per licensing term available to you. This one is free under the Stoa Press AI License.
2. **`Fora execute`** — the agent presents the signed offer it chose. The Exchange verifies the signature and answers with a signed retrieval URL.
3. *Fetch* — the delivery edge verifies that signed URL and serves the bytes. The same bytes the door refused.
4. **`Fora report`** — the licence carried a usage-reporting obligation, so the agent files a report and gets back a `report_id`.

That last step is the one people skip when they imagine this problem. The licence is not only permission to read; it carries obligations, and the protocol makes discharging them part of the transaction rather than a promise.

<Aside type="tip" title="An offer sells exactly one term">
A resource with three licensing arrangements yields three offers, each priced from the term it sells. The agent chooses an *offer*, not a term, and executes that. See [Licensing terms](/protocol/licensing-terms/).
</Aside>

## Doing it without MCP

The tools above are ergonomics. The wire is [Connect](https://connectrpc.com/) over HTTPS, and the same exchange looks like this:

```bash
EX=https://exchange.demo.fora-protocol.org

# Discovery — requires a signed request; see Authentication for the signature base.
curl -sS "$EX/fora.v1.ExchangeService/DiscoverResources" \
  -H 'Content-Type: application/json' \
  -H 'Signature-Agent: https://agent-duci2vuk.mcp.demo.fora-protocol.org' \
  -H 'Signature-Input: ...' -H 'Signature: ...' \
  --data @query.json
```

with `query.json`:

{/* fora-validate: ResourceQuery */}
```json
{
  "ver": "1.0",
  "exchange": "exchange.demo.fora-protocol.org",
  "requester": {
    "id": "my-agent",
    "domain": "agent-duci2vuk.mcp.demo.fora-protocol.org",
    "type": "REQUESTER_TYPE_AGENT",
    "scopes": ["*"]
  },
  "uris": ["https://demo.fora-protocol.org/articles/philosophers/md/leucippus.md"]
}
```

`ExecuteTransaction` and `ReportUsage` follow the same shape. Rather than hand-rolling the RFC 9421 signature, use an SDK — Go, TypeScript and Python are published, and each ships the signing transport, the offer verifier and the usage-report client:

- [Agent SDK overview](/components/agent-sdk/overview/) — the client faces and how they compose
- [Transaction flow](/protocol/transaction-flow/) — the full message sequence with payloads
- [Authentication](/protocol/authentication/) — what each signature covers, and why

## What you just proved

- An agent can obtain a **verifiable network identity** in minutes, with a published key and a revocation path.
- A publisher can **refuse agents wholesale** and still sell to them, without allow-lists or bilateral contracts.
- Access is **priced, signed and reported**, with the accepted terms pinned by digest at registration.
- None of it required a human in the loop after consent — and none of it required the publisher to know who you are in advance.
