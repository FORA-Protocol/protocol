## The Problem

AI agents need resources. Not just web pages — court filings, academic papers, credit reports, medical imaging, satellite data, drug interaction databases, live market feeds. These resources are scattered across thousands of providers, each with their own API, pricing model, authentication scheme, and terms of use.

Today, every integration is bespoke. An agent that needs a D&B credit report speaks a completely different protocol than one that needs a PACER court filing or a DrugBank interaction check. There is no common way to discover what's available, negotiate a price, execute a transaction, verify what was delivered, or dispute a problem.

The result: agents are locked into whichever providers their developers happened to integrate. Providers who want to serve AI agents must build custom APIs for each consumer. Neither side scales.

## What FORA Does

FORA — the **Federated Open Resource Access** — is an open transaction layer for metered resource access by AI agents. One protocol for discovering, pricing, transacting, delivering, and verifying digital resources.

```
Agent → Broker → Exchange → Resource
         (routes)       (prices)      (delivers)
```

**For agents:** Query any Exchange. Compare offers across providers. Pay per use. Verify what you got.

**For resource providers:** Expose your catalog through an Exchange. Set your price. Get paid per access. No custom integrations per consumer.

**For Exchange operators:** Aggregate provider catalogs. Handle transactions. Earn a margin. Compete on coverage, quality, and price.

## How It Works

A FORA transaction follows six steps:

```
1. Discover    Agent checks /.well-known/fora.json → finds Exchange endpoint
2. Query       Agent calls DiscoverResources → gets Offers with pricing + attestations
3. Transact    Agent calls ExecuteTransaction → gets delivery instructions + billing_id
4. Deliver     Agent fetches resource via signed URL → expires, optionally bound to the agent's key
5. Report      Agent calls ReportUsage → reports consumption (tokens, pages, minutes, records)
6. Dispute     If needed: DisputeTransaction → evidence-based dispute with report_id
```

## One Protocol Across Industries

The same messages price a news article by the token, a court filing by the page and satellite imagery by the square kilometer. Each offer names its metering unit in `Pricing.unit`:

| Industry | Resource | `Pricing.unit` |
|----------|----------|----------------|
| News/Media | Articles, podcasts, live broadcasts | `tokens`, `minutes` |
| Legal | Court filings, legislation, patents | `pages`, `items` |
| Finance | Stock quotes, credit reports | `records`, `minutes` |
| Academic | Journal articles, preprints | `tokens`, `items` |
| Medical | Clinical trial data, imaging studies | `records`, `images` |
| Government | Property records | `records` |
| Geospatial | Satellite imagery | `sq-km` |
| Pharma | Drug interaction lookups | `calls`, `pharma:interaction_pairs` |
| Media monitoring | Continuous news feeds | `minutes` |

Every unit in the table is in the protocol's [registered list](/reference/proto-fora/#pricingmodel) except `pharma:interaction_pairs`. A unit outside that list carries a namespace of its own, as that one does; a bare unregistered unit is rejected when the catalog is ingested. Through a Broker, one purchase can hold items from several Exchanges, each priced in its own unit.

What differs between industries is the unit, the resource's mutability and the domain metadata in the `ext` fields. The messages are the same.

## Key Design Decisions

### Unit-agnostic metering

Pricing uses `rate` + `unit` + `estimated_quantity`: a metered purchase charges the estimate times the rate, or one unit at the rate when the offer states no estimate. `unit_cost` is a normalized figure for comparing offers across Exchanges. No assumption about what's being metered. The unit is a registered one, such as `tokens`, `pages`, `seconds`, `records` or `sq-km`, or a namespaced one of your own, such as `pharma:interaction_pairs`.

### Content mutability

Every resource declares whether it's **static** (articles, patents — hash is stable), **dynamic** (credit reports, drug databases — content changes between offer and fetch), or **live** (streaming feeds — no content exists at offer time). This decides whether the agent checks the content hash on delivery, and whether a hash mismatch can be disputed.

### Data freshness

Offers carry `data_as_of` — when the data was current. Agents set `max_data_age` — how fresh they need it. The Broker should drop offers older than that. Examples: a credit report updated within the last week, a drug database updated this month.

### Extension profiles

Domain metadata is governed in three layers:

| Layer | What | Example |
|-------|------|---------|
| **Core proto** | Fields defined in `fora.proto` | `resource_mutability`, `data_as_of` |
| **Standard extensions** | Cross-domain conventions in `fora.*` namespace | `fora.attestation.claims_schema` |
| **Domain profiles** | Industry-specific vocabularies | `news.iptc_guid`, `academic.pmid`, `legal.legislation.eli` |

Exchanges declare which profiles they support. Agents declare which profiles they understand. A Broker forwards the agent's profiles to each Exchange, and each Exchange answers for its own.

Six v1 profiles exist:
- **[fora-news-v1](/protocol/ext-news/)** — articles, podcasts, broadcasting (IPTC NewsML-G2, Podcasting 2.0)
- **[fora-academic-v1](/protocol/ext-academic/)** — scholarly articles, preprints (CrossRef, OpenAlex, COUNTER 5.1)
- **[fora-legal-v1](/protocol/ext-legal/)** — legislation, case law, patents (ELI, ECLI, Akoma Ntoso)
- **[fora-comp-v1](/protocol/ext-comp/)** — IAB Tech Lab CoMP V1 metadata
- **[fora-c2pa-v1](/protocol/ext-c2pa/)** — C2PA provenance results and training and mining restrictions
- **[fora-music-v1](/protocol/ext-music/)** — music recordings and the works they record (ISRC, ISWC, IPI)

### Identity and authorization

Every request carries a `Requester` message — a universal actor identity with fields for `id`, `domain`, `type`, and `scopes` (request authentication is a separate RFC 9421 HTTP Message Signature in the headers, not a field on `Requester`). The Requester is not limited to AI systems: any entity that needs metered access — autonomous agents, human-operated copilots, enterprise service accounts, research pipelines — uses the same identity model.

**RequesterType** classifies the caller: `AGENT` (autonomous), `HUMAN_TOOL` (copilot), `SERVICE` (enterprise pipeline), `DELEGATED` (acting on behalf of another), `RESEARCH` (batch data collection).

**Scopes** are the Requester's signed statement of what it is entitled to. Examples: `subscription:marketdata-2026`, `credit:read`, `academic:*`, `*` (unrestricted). They decide which license terms the Exchange presents, and a Requester never learns of a resource outside its scopes. The Exchange does not verify them; a false statement is traceable to the key that signed it. An Exchange may instead gate a term behind a verified delegation; then only the delegation chain's verified scopes count for that term.

**Delegation with JWTs** enables offline-verifiable, narrowable authorization. An issuer the verifier trusts, such as the resource owner or a subscription provider, issues a root delegation JWT bound to a principal's key. Each holder in the chain can narrow permissions by issuing a child delegation JWT — restrict scopes, lower spend caps, shorten expiry — but can never widen them. A chain holds at most four tokens, and the verifier needs only the issuer's public key, with no call to the issuer.

**Request signatures** are carried in the HTTP headers, whoever sends the request. Each party signs the request it sends with one labeled RFC 9421 HTTP Message Signature. A Broker originates its own discovery queries and re-packages execute requests, signing each alone, and on a purchase the agent's identity and consent travel in the body as `AgentAcceptance`. The Exchange counts the signatures against its `max_intermediary_hops` before verifying any, then verifies the request signature.

**`ext_critical`** flags extension keys the receiver of a message MUST understand: on a request, the party that receives it; on an offer, the agent. See [Extension Profiles](/protocol/extension-profiles/) for details.

For the full identity model — key lookup, child delegation JWT examples, scope-based catalog filtering, and denial reasons — see [Authentication](/protocol/authentication/).

### Cryptographic attestation

Providers and third-party verifiers sign claims about resources using Ed25519. Three levels: none (just identifiers), self-attested (provider signs), third-party verified (independent verifier signs). Agents choose what to trust.

### Dispute chain

No fire-and-forget disputes. The agent must file a `UsageReport` before disputing, creating an evidence chain: each `DisputeRequest` names the transaction and the `report_id` of its usage report. The Exchange refuses a filing that fails a check, such as a missing usage report or a closed dispute window, with a typed reason. The protocol standardizes the dispute signal, its states and its outcomes (credit, redelivery, rejection or further investigation); how an Exchange decides a dispute is up to the Exchange. See [Dispute Resolution](/protocol/dispute-resolution/).

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                       DEMAND SIDE                           │
│                                                             │
│   AI Agent ──→ Broker                                       │
│   (needs resources)   (routes queries, compares offers,     │
│                        enforces budgets)                    │
└───────────────────────────┬─────────────────────────────────┘
                            │ DiscoverResources / ExecuteTransaction
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                       SUPPLY SIDE                           │
│                                                             │
│   Exchange ──→ Resource Provider ──→ Delivery Endpoint      │
│   (catalog, pricing,   (owns content,    (CDN, API, PACS,  │
│    transactions)        sets terms)       DICOMweb, etc.)   │
└─────────────────────────────────────────────────────────────┘
```

The Broker is optional — agents can query Exchanges directly. A Broker queries several Exchanges, merges their offers, and can filter them by the agent's budget and data freshness.

## Scope

FORA covers **metered access to resources that exist**. The test: "Does the resource exist before the transaction?"

| In Scope | Out of Scope |
|----------|-------------|
| Static resources (articles, papers, patents) | Job execution (translation, ML inference) |
| Dynamic resources (credit reports, drug DBs) | Document generation |
| Streaming resources (quote feeds, live audio) | Compute services |
| Database lookups (drug interactions, property records) | |

## What Exists Today

- **The wire format**: the `fora.v1` and `fora.admin.v1` protobuf packages, with a [JSON Schema](/reference/json-schemas/) for each message. See [Proto: FORA v1](/reference/proto-fora/).
- **SDKs in three languages**: <a href={PACKAGES.go.url}><code>{PACKAGES.go.coordinate}</code></a> for Go, <a href={PACKAGES.ts.url}><code>{PACKAGES.ts.coordinate}</code></a> on npm and <a href={PACKAGES.python.url}><code>{PACKAGES.python.coordinate}</code></a> on PyPI.
- **Six extension profiles**: [news](/protocol/ext-news/), [academic](/protocol/ext-academic/), [legal](/protocol/ext-legal/), [CoMP](/protocol/ext-comp/), [C2PA](/protocol/ext-c2pa/) and [music](/protocol/ext-music/).
- **Two live demos** on a demo Exchange. In [First License](/getting-started/poc-walkthrough/), an agent buys a license to an article whose site refuses its direct request. In [Music](/getting-started/live-demo-music/), an agent buys two different licenses to the same track.
- **FORA Server**: an [open-source implementation](https://github.com/FORA-Protocol/reference-implementation) of the Exchange, the Broker, an identity service with an MCP adapter, and the edge function.
- **The standards it builds on**: IAB Tech Lab's CoMP V1 is mapped field for field and carried as the `fora-comp-v1` profile. The RSL 1.0 AI-use terms seed FORA's restriction vocabulary. See [Standards Layering](/protocol/standards-layering/).
