---
title: "JSON Schemas"
description: "Validate a FORA message against the published per-message JSON Schemas, in a default or a strict variant."
---

Every release publishes one JSON Schema (draft 2020-12) for each message of the wire
contract, `fora.v1` and `fora.admin.v1`. An implementer or a conformance harness can
check the shape of a FORA message against them, in any language, without the SDK.

The schemas are generated from the proto by the same pinned generator the SDK models are
built from (`bufbuild/protoschema-plugins` `protoc-gen-jsonschema` v0.6.0), so they carry
the per-field `buf.validate` constraints. CI regenerates them on every change and fails
if the committed files differ.

## Two variants

Each message has two files, named by its fully-qualified name:

| File | Unknown fields |
|---|---|
| `fora.v1.ResourceResponse.schema.json` | Accepted. A reader that must accept messages from a newer protocol version uses this variant. |
| `fora.v1.ResourceResponse.schema.strict.json` | Refused: `additionalProperties` is `false` on every message object, at every depth. A conformance check uses this variant, so an unknown or misspelled field fails. |

Each file is self-contained. The message is the document root, and every message it
references is inlined under `$defs`, keyed by its fully-qualified name. One file is
enough to validate a message, with no schema registry and no network access.

## Where to get them

The schemas ship in all three published packages, at the version you pin:

| Package | Access |
|---|---|
| Go module `github.com/FORA-Protocol/protocol` | The `gen/jsonschema/` directory. Package `github.com/FORA-Protocol/protocol/gen/jsonschema` embeds it: `jsonschema.Load("fora.v1.ResourceResponse", true)` returns the strict variant, and `jsonschema.FS` holds every file. |
| `fora-protocol` on PyPI | `wire.schemas.load("fora.v1.ResourceResponse", strict=True)` returns the schema as a `dict`. `wire.schemas.names()` lists the messages. |
| `@fora-protocol/sdk` on npm | The export path `@fora-protocol/sdk/jsonschema/*`, for example `@fora-protocol/sdk/jsonschema/fora.v1.ResourceResponse.schema.strict.json`. |

## Validate a message

Python, with the `jsonschema` library:

```python
from jsonschema import Draft202012Validator
from wire import schemas

validator = Draft202012Validator(schemas.load("fora.v1.ResourceResponse", strict=True))
validator.validate(body)  # raises ValidationError on an unknown field or a constraint violation
```

TypeScript, with Ajv, which `@fora-protocol/sdk` already depends on:

```ts
import Ajv2020 from "ajv/dist/2020.js";
import schema from "@fora-protocol/sdk/jsonschema/fora.v1.ResourceResponse.schema.strict.json" with { type: "json" };

const validate = new Ajv2020({ validateFormats: false }).compile(schema);
if (!validate(body)) console.log(validate.errors);
```

Go reads the file with `jsonschema.Load` and passes the bytes to any draft 2020-12
validator.

## What the schemas accept

The schemas describe canonical proto-JSON as the FORA wire carries it. The two variants
differ only in the unknown-field policy; everything below applies to both.

- **Field names are the proto field names, in snake_case.** That is the FORA wire
  naming: servers render proto-JSON with the proto names, the SDKs send them, and the
  canonical signing form uses them. A lowerCamel key such as `offerGroups` is an unknown
  field, so the strict variant refuses it.
- **`google.protobuf.Struct` stays open.** Every `ext` field is a Struct: a JSON object
  whose keys the contract does not define. The strict variant never closes a Struct, at
  any depth. A map field keeps its value schema.
- **64-bit integers accept a decimal string or a JSON integer.** Canonical proto-JSON, and
  so a FORA server, emits an `int64` as a string; the SDKs send a JSON number. A bound
  applies to both forms: `Quota.limit` must be at least 1, so both `0` and `"0"` fail.
- **Other numbers are JSON numbers.** Proto-JSON parsers also accept an `int32` or a
  `double` as a string, but no FORA sender emits that form, and accepting it would let a
  string such as `"1000"` past a numeric bound.
- **Constraints.** String patterns and lengths, numeric bounds, enum restrictions and item
  counts are carried from `buf.validate`. A field whose zero value its own rule rejects is
  `required`, because proto-JSON omits a zero value, so an omitted field is that zero
  value. A `repeated.unique` field carries `uniqueItems`.
- **Enums** accept the value name, which FORA senders emit, or the number of a permitted
  value, which proto-JSON parsers also accept.

For example, the strict variant of `Quota` accepts this message:

```json
{ "limit": "5", "metric": "accesses", "window": "QUOTA_WINDOW_DAILY" }
```

It refuses the same message with `"limit": "0"` (the bound), without `metric` (a required
field), or with an added `"metricName": "accesses"` (an unknown field).

## What the schemas do not check

- **Cross-field rules.** A rule that relates two fields, such as which pricing fields a
  pricing model requires, cannot be expressed per field. Servers enforce these rules, and
  the SDKs apply them too.
- **Oneof exclusivity.** A schema does not refuse two members of the same oneof.
- **Formats.** `format` (`date-time`, `duration`) is an annotation unless your validator
  is configured to assert formats.

A message that passes the strict schema has the right shape and field-level values; a
server can still refuse it for a cross-field rule, a signature or the state of the
transaction.

## How the schemas are checked

- The drift gate regenerates the schemas from the proto and compares the files byte for
  byte, as it does for the generated code.
- A Go conformance test checks the file set, the field names and the unknown-field policy
  against the compiled proto descriptors.
- Both variants must reach the verdict of Go `protovalidate` on every case of the
  conformance corpus, in Python (with `jsonschema`) and in TypeScript (with Ajv).
